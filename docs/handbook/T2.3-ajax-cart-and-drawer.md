## 1. Concept

### The Cart AJAX API — five endpoints, one gotcha

Storefront-side, same-origin, no auth. Stable for years:

| Endpoint | Does | Notes |
|---|---|---|
| `GET /cart.js` | Current cart as JSON | `items`, `item_count`, `total_price` |
| `POST /cart/add.js` | Add item(s) | `{ items: [{ id: variantId, quantity, properties }] }` — or just post the product form's FormData |
| `POST /cart/change.js` | Change one line | `{ line: <key>, quantity }` — `quantity: 0` removes it |
| `POST /cart/update.js` | Bulk updates, note, attributes | `{ updates: {...}, note, attributes }` |
| `POST /cart/clear.js` | Empty the cart | |

Three professional details:

- **Money is in cents.** `total_price: 4599` is $45.99. Every threshold comparison happens in cents; T1.1's gotcha, now with consequences.
- **Address lines by `key`, not index.** Each cart item has a stable `key`; `change.js` accepts either, but 1-based indexes shift when lines vanish. Key is the grown-up choice.
- **Errors are content.** `add.js` answers `422` with a human-readable `description` when it can't add (sold out, stock cap hit). A silent failure here loses real money — surfacing that message is part of the build.

### The pattern that changes everything: `sections`

The write endpoints accept a `sections` parameter:

```js
body: JSON.stringify({
  items: [{ id: 12345678, quantity: 1 }],
  sections: 'cart-drawer,cart-icon-bubble'
})
```

The response then carries **server-rendered HTML for those sections**, fresh, reflecting the new cart. You swap that HTML into the DOM. No client-side templating, no duplicated price logic, no locale bugs — Liquid stays the single source of truth for markup, and JS becomes a courier. (Standalone flavor: `GET /?sections=cart-drawer` — the Section Rendering API — same idea without a mutation.)

**This is the architectural insight of the tutorial:** anything you render *inside* the drawer section in Liquid gets updated on every cart change **for free**. Your free-shipping bar will need zero JavaScript of its own for exactly this reason.

### Dawn's cart architecture — extend it, never rebuild it

Dawn already ships the whole machine:

```
[Add to cart click]
  → product-form.js (ProductForm custom element intercepts submit)
    → fetch /cart/add.js  { …, sections: [drawer, bubble] }
      → cart-drawer.js swaps returned HTML into the drawer + header bubble
        → publish(cartUpdate) via pubsub.js → drawer opens, listeners react
```

Plus: `sections/cart-drawer.liquid` (the markup you'll extend), a cart-notification alternative, and a theme setting choosing drawer / notification / page. On Dawn-based client work, **the job is almost never "build a cart drawer" — it's "enhance the one that exists."** Rebuilding what ships is how juniors introduce the bugs the two-regression rule exists to prevent. (On a theme *without* a drawer, these same patterns are how you build one — the skills transfer.)

Never-break, cart edition: publish through the theme's pubsub so apps and components hear changes · never intercept the **checkout** button — it stays a plain submit to `/checkout` · extend `product-form`, don't replace it.

### The two enhancements, designed

**Free-shipping bar.** Pure Liquid inside the drawer: a threshold setting (merchants think in dollars — store it as a number and `| times: 100` into cents consciously), three states (empty cart · "You're {remaining} away" · "You've unlocked free shipping 🎉"), a progress element whose width is `total / threshold` capped at 100%. Scope note that saves client conversations: **the bar is marketing UI** — actual free shipping is configured in Settings → Shipping (or via Functions, T4.3). Sell them as one deliverable, know they're two systems. (Multi-currency stores: the threshold lives in shop currency — flag it as a scoping question on Markets-heavy clients, don't solve it today.)

**Upsell slot.** Merchant-picked product via a `product` setting on the drawer section, rendered as a mini card — with three Liquid guards: hidden when unset, hidden when unavailable, **hidden when already in the cart** (loop `cart.items`, compare product ids). The Add button is the elegant part: wrap a minimal `/cart/add` form in the theme's own `<product-form>` element — Dawn's JS then gives you AJAX, section re-render, and the drawer update *for free*. Dynamic upgrade for later: Shopify's recommendations endpoint (`/recommendations/products.js?product_id=…&intent=complementary`) can replace the manual pick.

## 2. Woo bridge

| You know (Woo) | Here (Shopify) | Where the mapping breaks |
|---|---|---|
| Cart fragments — rendered HTML pushed to the mini-cart | `sections` param on cart endpoints | Same HTML-over-the-wire philosophy, done cleanly: explicit, per-section, documented |
| `add_to_cart_fragments` filter | `sections: 'cart-drawer,cart-icon-bubble'` | You *ask* for fragments per request instead of registering them globally |
| `admin-ajax.php` bottleneck; cache-exclusion chores for cart pages | First-class endpoints; platform handles cart dynamics | A whole category of Woo performance pain simply absent |
| `WC()->cart` in PHP, hooks like `woocommerce_add_to_cart` | `cart` object in Liquid + `/cart.js` in JS — **no server-side add hook** | The interception reflex has no home here; cart/checkout *validation* lives in Functions (T4.3) |
| jQuery `added_to_cart` event | Theme pubsub `cartUpdate` | Publish so apps can hear — same treaty, new bus |
| Mini-cart widget | Drawer / notification section | Merchant-composable, section-rendered |
| Float dollars | **Cents, everywhere** | Threshold math, comparisons, progress — all in cents until the last `money` filter |

## 3. Claude Code drill — enhance the drawer

Branch: `t2-3-cart-drawer`. Prep: ensure your dev store's drawer is enabled (theme settings → cart type: drawer) and one product has inventory tracking on with **quantity 1** (you'll need it to force an error).

### Part A — Trace and touch (~45 min)

1. **Trace the machine.** With devtools **Network tab open**, add a product to the cart. Find the `add.js` request: read the payload (there's the `sections` list) and the response (JSON + rendered HTML). Then walk the code path — `product-form.js` → `cart-drawer.js` → `pubsub.js` — with Claude Code annotating and you verifying, T1.2-style. Output: `notes/cart-flow.md`, the diagram in your own words.
2. **Touch the API raw.** From the storefront console:
   ```js
   fetch('/cart.js').then(r => r.json()).then(console.log)
   ```
   Then add your inventory-1 product **twice** via fetch and read the `422` description that comes back the second time. Change a line to `quantity: 0` using its `key`. Five minutes of poking buys permanent API literacy.

### Part B — The free-shipping bar (Liquid only)

Spec it by hand (settings: enable checkbox, threshold number in store currency, achieved message text), then build **inside `sections/cart-drawer.liquid`** — spec-first prompt, review protocol. The three states, the capped progress width, cents math via `times: 100`, `money` only at output.

**Then prove the architecture:** with the Network tab open, add and remove items. Watch the drawer HTML return on each mutation and the bar move — *you wrote no JavaScript for this*. That's the `sections` pattern paying rent. Check the bar at 360px while you're there.

### Part C — The upsell slot

Spec: `product` picker setting + the three guards. For the Add button, **pattern-match the theme**: find an existing minimal `product-form` usage in this Dawn version (quick-add or featured product are good hunting grounds), and instruct Claude Code to mirror *that* wiring — with the current source in front of it — rather than inventing form markup from memory. Review with suspicion on exactly that point: does the upsell add flow through the same `add.js` + sections + pubsub path as the main form? Prove it in the Network tab.

Guards proven: pick a product → card shows · add it to cart → card disappears from the re-rendered drawer · unset the setting → slot gone entirely (view source: no empty wrapper).

*Stretch, optional:* swap the manual pick for `intent=complementary` recommendations for the first cart item — JSON fetch, small render, same guards.

### Part D — The proofs

1. **Full purchase flow** — drawer → checkout → Bogus gateway test order. The QA habit, now with your code in the path.
2. **Error made visible:** add the inventory-1 product twice through the UI — the customer must *see* the stock message, not silence.
3. **Coexistence:** console clean through every interaction; checkout button never intercepted; cart page (`/cart`) still works.
4. **Widths:** 360 / 390 / 768 on the drawer with bar + upsell present.

### Part E — Package it

Delivery notes from Template 3 — settings walkthrough, the marketing-UI-vs-shipping-settings scope note, assumptions. Flag it in the notes as **demo-store material**: this exact deliverable, polished, is proof-kit item #1's centerpiece. Commit.
