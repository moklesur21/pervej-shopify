## 1. Concept

### A. What an app actually is — the full inventory

T0.2 gave you the one-liner: *plugin = PHP inside your site; app = external service + sanctioned surfaces.* You've since **built** three of those surfaces yourself. Here's the complete map of where an installed app can appear:

| Surface | What it is | You met it |
|---|---|---|
| **App blocks** (theme app extension) | Merchant-placeable blocks inside sections that accept `@app` | T1.3 — your own schemas accept them |
| **App embeds** (theme app extension) | Floating/invisible page-level elements, toggled in the theme editor | T3.1 — the diagnostic switchboard |
| Checkout UI extensions | Sandboxed checkout components | T4.2 — you built two |
| Functions | Discount/delivery/payment/validation logic | T4.3 — you built one |
| Web pixels | Sandboxed analytics subscriber | T5.1 — you built one |
| Post-purchase / thank-you / customer-account extensions | The after-money surfaces | T4.1 |
| Admin extensions | Blocks and actions inside the admin UI | New — know it exists |
| Its own backend | APIs + webhooks, off-platform | T5.2 — you built one |
| **Legacy: ScriptTag injections** | Blanket script on every page | Red flag on sight |
| **Dark past: direct theme-code edits** | Apps that wrote snippets into the theme | **This is where T3.1's ghosts come from** |

Read that table again with the right emotion: an installed app is *someone else's version of what you now build.* That symmetry is why you can evaluate them better than almost anyone — you know exactly what each surface costs and what clean looks like.

**Theme app extensions deserve one more beat**, because they're the modern contract: app assets hosted on Shopify's infrastructure, **app blocks loading only on pages where they're placed**, everything versioned with the app's deploys, nothing written into the theme's files. Upgrade-safe by architecture. When an app's storefront presence is blocks and scoped embeds, that's a green flag; when it's ScriptTags everywhere or theme edits, you're looking at rent *and* risk.

### B. When theme code isn't enough — the decision framework

The reflex to retrain: Woo's *"there's a plugin for that"* becomes **"is that a metaobject and a section?"** — asked first, every time. Your Module 1 skills make a surprising share of "app" asks into afternoon builds: FAQs, size charts, lookbooks, trust badges, upsell slots, quick filters — metaobjects + sections + zero monthly rent. Then the honest fork:

**An app earns its place when the ask needs:**
- **A backend and state beyond platform data** — reviews with moderation queues, Q&A, wishlists synced across devices
- **An ongoing service** — subscription billing with dunning, loyalty ledgers, live chat, advanced search relevance
- **Compliance or network machinery** you shouldn't own — payments-adjacent flows, marketplace syncs
- **Maintained complexity** whose upkeep would eat your retainer alive

**Custom (your Module 4–5 skills) beats both when** the logic is store-specific and small: a config-driven Function, a checkout field, a pixel, a webhook service — built once, no rent, owned by the client.

**The rent framing** that agencies remember: an app is a **monthly fee forever + a performance cost on every visit + a data-custody question**; custom is a build cost once + maintenance. Neither is always right — but only one of the three options gets *measured* in most agencies, and after today, you measure all three.

### C. The evaluation method — Template 6 (`app-evaluation.md`)

```markdown
# App evaluation — [app] for [need] · [store] · [date]

## 1. Fit
The actual ask: [one sentence] · Does this app solve it (not something adjacent)? 
Config depth vs. need: [under / matched / over-engineered]

## 2. Integration surface (verified on install, not assumed)
Blocks: [which] · Embeds: [which, default state] · ScriptTags/theme edits: [any = flag]
Theme diff after install: [clean / touched files]

## 3. Performance cost (measured, 3-run medians, mobile)
Product page before: [LCP/score] · after: [LCP/score] · **Δ = [the number]**
Requests added: [n] · Weight added: [kB] · Loads on pages without the feature? [y/n]

## 4. Data custody & exit
Where the data lives: [platform metafields / their cloud] · Export path: [what you get]
Uninstall test: [embeds gone? refs dangling? weight back to baseline?]

## 5. Quality signals
Reviews (recent-weighted): [read 10 newest] · Built for Shopify badge: [y/n]
Update cadence · support reputation: [notes]

## 6. Cost math
App: $[x]/mo → $[12x]/yr  vs  custom build: [your honest estimate] + upkeep
Break-even and 3-year picture: [two lines]

## 7. Plan/surface interactions
Checkout surfaces needed? → T4.1 checkpoint result: [.]

## Verdict
[ adopt / adopt with notes / reject → build custom / reject → alternative app ]

## Client summary (forwardable, 4–6 sentences, plain language)
```

Sections 3 and 4 are your differentiation: **numbers and an uninstall test.** Most evaluations in this industry are vibes plus star ratings.

### D. Integrating an app block *cleanly* — the craft standard

1. **Placement through the editor**, into sections that accept `@app` — never code hacks to force position.
2. **Style the wrapper, never the internals.** Spacing, width, and context come from the hosting section; reaching into the app's DOM with CSS overrides is a time bomb that detonates on the app's next update — the exact fragility your own extension work taught you to design out.
3. **Configure inside the app's settings** where offered (colors, typography) — that's the supported styling path.
4. **Document it**: which app, what config, where placed, the measured delta — in the delivery notes. An undocumented app is a future archaeology project.

## 3. Claude Code drill — reviews, evaluated and integrated

Client-shaped brief: *"The client wants product reviews."* The canonical block-based candidate: a free-tier reviews app (Judge.me's free plan is the traditional pick — any reviews app with app blocks and a free tier works). Branch `t5-3-reviews` for theme-side changes and notes.

### Part A — Pre-flight baselines (~25 min)

Git clean · **3-run median Lighthouse** on the product page (T3.2 discipline — these are the before photos for section 3) · screenshot the editor's current block picker and embed list. You cannot measure a delta you didn't baseline.

### Part B — Desk evaluation, verdict withheld (~40 min)

Fill Template 6 sections 1, 5, 6, 7 from the listing and docs alone — read it like T0.2's skeptic, now armed: ten newest reviews, badge check, pricing math. For section 6, estimate the custom alternative *honestly* — you can now actually price a metaobject-driven reviews build (display + capture form + moderation via metaobject status… feel where it gets expensive: moderation UX and spam are why reviews usually justify an app). Predict section 2 from the docs. Verdict: **provisional**.

### Part C — Install and inspect (~45 min)

Install on the dev store, then verify every prediction:

1. **What appeared?** Editor: new app blocks in the picker · embeds list (what got toggled on by default — turn off anything not needed).
2. **Place the blocks properly:** star-rating block into `main-product` (it accepts `@app` — your T1.3 knowledge, from the other side), review-widget block below. Add two test reviews so the render is real.
3. **`git diff` the theme** — modern apps touch nothing; witness it (or catch the exception and flag it in section 2).
4. **Network tab:** what loads, from where, how heavy · does it load on the homepage where no block is placed? (App-block architecture says no — verify.)
5. **After-photos:** 3-run median Lighthouse → **record the delta.** That number is section 3, and it's the line agencies quote you for.

### Part D — Integrate cleanly (~30 min)

Wrapper-level polish only: spacing and width from the hosting section, app-side settings for colors/typography, mobile widths checked. Write the one-sentence discipline into the notes: *internals unstyled because app updates own that DOM.* If something genuinely can't be achieved without reaching inside — that's an evaluation finding (section 1: config depth), not a license to hack.

### Part E — The uninstall proof (~25 min)

Uninstall the app. Then audit like it's a T3.1 engagement: embeds gone? blocks vanished from the picker? **any dangling block refs left in `product.json`** (pull and diff — observe what uninstall actually does)? network weight back to baseline? Record every answer in section 4 — exit cost is now measured, not assumed. Then **reinstall and re-place** (the deliverable stands; the eval doc keeps the uninstall evidence).

### Part F — Verdict and package (~25 min)

Complete Template 6 with measured data · final verdict · the forwardable client summary. Delivery notes (Template 3) for the integration itself: app, config, placement, delta, custody note. Save Template 6 to `notes/templates/` — and add tonight's meta-line to the productization list: *the evaluation method itself is pitch material — "we evaluate apps with measurements" is a sentence competitors can't say.*

## 4. Verification checklist

- [ ] Baselines captured before install: git state, 3-run medians, editor screenshots
- [ ] Desk evaluation done first, custom-build estimate honestly priced, verdict withheld
- [ ] Install inspected: blocks/embeds inventoried, unneeded embeds off, theme diff checked
- [ ] Blocks placed via editor into `@app`-accepting sections; two test reviews rendering
- [ ] Performance delta measured and recorded — the number exists
- [ ] Clean-integration standard met: wrapper styling only, app settings used, mobile checked
- [ ] Uninstall proof run: embeds, refs, weight all audited and documented; app reinstalled
- [ ] Template 6 complete with verdict + forwardable summary; delivery notes written; branch committed
