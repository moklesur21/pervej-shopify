## 1. Concept

### What a Function is — and the constraints that define it

A Shopify Function is your logic, compiled to **WebAssembly**, executed *by Shopify's servers* at a sanctioned decision moment — pricing a cart, listing shipping options, offering payment methods, validating checkout. Scripts (the old Plus-only Ruby sandbox) are **fully retired since June 2026**; Functions are the only game, and unlike Scripts they're not Plus-exclusive by nature (plan gating varies per API — the T4.1 checkpoint applies here too).

The execution contract is brutal and liberating:

- **Pure input → output.** No network calls, no randomness, no clocks, no side effects. Deterministic by construction.
- **Tiny budget.** Instruction-count and memory limits in the run-it-in-milliseconds class — this executes inside the checkout's hot path.
- **You don't run it. Shopify does.** You ship compiled logic; the platform invokes it with data and applies what you return.

The consequence that shapes all real-world Function work: **anything your logic needs to know must arrive in the input** — which is why configuration lives in **metafields and metaobjects** (Winter '26 made app-owned metaobject reads native). The pattern: merchant edits a rule in admin data → your function reads it in the input → behavior changes **with no deploy**. Config-driven Functions are also prime productization material — a rule engine built three times is a plugin waiting to happen.

### The shape: three files, one contract

A Function extension (it lives in your T4.2 app — same `generate`, same `deploy`, same versions) is essentially:

1. **`shopify.extension.toml`** — which Function API this targets.
2. **An input query (GraphQL)** — you declare exactly what data you want: cart lines, cost, buyer identity, attributes, shop/product metafields. Shopify resolves it and hands you the result.
3. **The logic** — **JavaScript** (compiled to Wasm via Javy — your accessible path) or **Rust** (first-class, for when budgets pinch). It receives the input, returns **operations** — structured JSON declaring what should happen.

```
input query (what you need) → your pure function → operations (what to do)
```

One professional detail to hunt in every review: **money arrives as decimal strings** in Function inputs. Handle amounts with the scaffold's idioms, never casual `parseFloat` float math — the cents discipline from T1.1, now with legal tender.

### The sockets — what Functions can decide

| Function API | Decides | The client ask it answers |
|---|---|---|
| **Discount** (the unified API — one function can apply product, order, and shipping discount classes) | Automatic pricing logic | "10% off over $100" · "VIP customers get 15%" · volume tiers |
| **Delivery customization** | Hide / rename / reorder shipping options | "Hide express for PO boxes" · "Rename 'Standard' per market" |
| **Payment customization** | Hide / rename / reorder payment methods | "No COD under $50" — T4.1's scoping script #3, now buildable |
| **Cart & checkout validation** | Block progress with messages | "Max 2 per customer" · "No mixing preorder + in-stock" |
| **Cart transform** | Merge/expand cart lines | Bundles presented as one line |

Others exist at the edges (fulfillment constraints, order routing); the five above cover the overwhelming share of agency asks. Discount logic that used to require a paid dynamic-pricing plugin stack in Woo is native here — another license line item your quotes get to delete.

### Deployed ≠ active — the step everyone misses

Deploying a discount function ships *capability*, not behavior. A **discount must be created that uses it** — via an app-provided admin UI (real apps) or, for extension-only client work, an Admin GraphQL mutation (`discountAutomaticAppCreate`-family) pointing at your function. Your `app dev` session includes a GraphiQL console for exactly this. Internalize the two-step now and you'll never stare at a silent checkout wondering why nothing happens.

### The debugging surface

Two loops, use them in order: **local first** — `shopify app function run` executes your function against a JSON input fixture on your machine, no deploy, sub-second iteration; **then live** — every real invocation logs input and output in the app's dashboard (Function run logs), which is your production forensics on client stores.

| Hook code: runs in-process, full WP access, network, DB, anytime | Compiled Wasm: pure, offline, deterministic, milliseconds, fixed moments | The deepest break — conditionals sprawl becomes **config data**; `if` forests become metafields |
| Discount rule plugins (annual licenses) | Native Functions | Retired line item |
| `error_log()` archaeology | Local runner + dashboard run logs with input/output per invocation | Strictly better forensics |

## 3. Claude Code drill — a config-driven threshold discount

The build: **"Spend ≥ X, get Y% off the order"** — with X and Y living in a shop metafield the merchant can edit. Frictionless to test, sibling to your T2.3 free-shipping bar, and the config pattern in miniature. *(Stretch at the end adds the VIP-tag variant — the exact use case Shopify's own Editions notes cite.)*

Work in the T4.2 app repo, branch `t4-3-discount`.

### Part A — Generate and orient (~30 min)

`shopify app generate extension` → **Discount** function → **JavaScript**. Then the ritual: read all three pieces of the scaffold — TOML, the `.graphql` input query, the logic entry — before changing anything. Claude Code annotates; you verify one claim via the toolkit. Add one line to the app's `CLAUDE.md`: *Functions are pure — no network, no clocks, no randomness; money is decimal strings, handled per scaffold idiom.*

### Part B — Feel the walls locally (~20 min)

1. Run the scaffold as-is with `shopify app function run` against its fixture input. Read the output operations JSON — that's the whole contract, visible.
2. **Spring the trap:** add a `fetch(...)` call and a `Date.now()` to the logic, run again, and watch the sandbox refuse. Delete them. Two walls touched personally are two walls you'll never promise a client through.

### Part C — Spec, then build (~60 min)

**Spec by hand** in `notes/t4-3-spec.md`:

- The rule in English: cart subtotal ≥ threshold → percentage off the order; below → no operations.
- Edge cases decided *before* code: empty cart · subtotal exactly at threshold (inclusive) · config metafield missing or malformed → **no discount, never an error** (fail-closed) · multi-currency noted as out of scope, same caveat as T2.3.
- The input query, sketched by hand: cart cost + the shop metafield (`custom.threshold_discount`, JSON: `{"threshold": "100.00", "percentage": 10}`).

Then the master prompt: your spec + *"extend the scaffold's idiom; decimal-string money handling only; return an empty-operations result on any config problem; smallest complete implementation; list anything you couldn't express in this API."* Review hunts: float math on money · any nondeterminism · logic that throws instead of failing closed · invented input-query fields (the toolkit settles the schema).

### Part D — Wire the config (~20 min)

T1.5 muscle: define the shop metafield in Settings → Custom data (or via GraphiQL), set the JSON value. Update your local fixture to include it; `function run` until below-threshold and above-threshold fixtures both behave. Local loop green before anything touches a real checkout.

### Part E — Activate and prove (~45 min)

1. `shopify app deploy`.
2. **The second step:** in the `app dev` GraphiQL console, create the automatic discount that references your function (the `discountAutomaticApp` mutation family — let the toolkit supply the current shape; read what you send). Confirm it shows in admin → Discounts.
3. Checkout proofs, screenshots both: cart below threshold → no discount line · add items past it → the discount appears, correctly computed · complete a test order and see the discount **on the order**.
4. **The config payoff, witnessed:** change the percentage in the metafield, refresh checkout — new discount, **zero deploys**. Say the pattern out loud; it's the sentence that sells configurable Functions to agencies.

### Part F — Forensics and the map (~30 min)

1. Find your function's **run logs** in the dashboard; open one, read input and output. That's your client-store debugger — know the room before you need it.
2. Write `notes/functions-map.md`: the five sockets, one real client ask each, plan-gating column marked "verify per T4.1." Close the loop on T4.1's scoping script #3 — you can now build the COD answer, not just say it.
3. Add a line to the productization list: *config-driven discount/validation rules — extraction candidate on third build.*

**Stretch:** duplicate the function into a VIP variant — buyer identity in the input query, customer tag `VIP` → flat percentage. Requires a logged-in test customer at checkout; the login dance is the only new difficulty, which is exactly why it's the stretch.
