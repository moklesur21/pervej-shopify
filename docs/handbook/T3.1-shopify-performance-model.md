# T3.1 — The Shopify Performance Model
**Module 3 · Tutorial 14 of 26 · Est. 4–5 hours**

**Goal:** Learn where speed lives on this platform — the four levers you control, the half of your Woo playbook that's dead, and the **audit method** that turns a slow store into a ranked findings document. That document is service S1's intake artifact: it's how speed work gets scoped, quoted, and won.

**Prerequisites:** Module 2 complete. Today you diagnose; T3.2 you operate.

---

## 1. Concept

### The half you don't control — and never will

Shopify owns the infrastructure: global CDN, edge caching, HTTP/2+, compression, TLS, scaling, and the entire checkout. There is no hosting to upgrade, no PHP to tune, no database to clean, no page-cache plugin to configure — **that entire genre of Woo speed work has no equivalent here.** A baseline of platform scripts also ships on every store; treat it as a fixed cost.

Consequence: when a Shopify store is slow, it is almost always slow **in the front end you can see** — which means the remaining levers are fully yours, and excuses are scarce.

### The four levers you do control

**1. Images — the biggest lever on most stores.**
Shopify's CDN serves modern formats and exact sizes *if the theme asks correctly*: `image_url: width:` + `image_tag` (which generates `srcset`/`sizes`, and `width`/`height` so layout doesn't shift). The sins you'll find everywhere: images requested full-size into small slots (devtools shows rendered vs intrinsic size), missing lazy-loading below the fold, 3 MB uploads doing a 200 KB job, and the **LCP image treated like any other** — it must *not* be lazy, and deserves priority (`preload_tag`, or `fetchpriority: 'high'` passed through `image_tag`).

**2. JavaScript — the main-thread tax.**
Theme JS should already be small, deferred, per-section (Module 2 doctrine). The real villain is everything else: app scripts, pixels, chat widgets, review embeds, GTM containers stacked with tags. Symptoms: long tasks in the Performance panel, high unused-JS in Coverage, poor INP.

**3. Fonts.**
Use the theme's font settings (served from Shopify's font CDN), limit families and weights, `font-display: swap` (Dawn's `font_face` usage does this), preload only the critical face, and be suspicious of third-party font origins.

**4. App bloat — the platform's signature disease.**
Apps inject through **app embeds** (toggles in the theme editor — your first diagnostic switchboard), app blocks, and legacy script tags. Two facts define the epidemic: mid-size stores routinely run 20–40 apps, and **uninstalled apps can leave code behind** — leftover snippets and script references in the theme ("ghost code") that keep charging performance rent for a service nobody uses. Plugin bloat and app bloat are the same disease; your Woo instinct transfers whole.

One structural note: Liquid render cost exists (a mega-menu looping big collections on every page can drag TTFB) but on most stores it's a minor line item next to assets. Check it; don't start there.

### The metrics — and where the evidence lives

Core Web Vitals, mobile-first, current thresholds: **LCP ≤ 2.5 s · CLS ≤ 0.1 · INP ≤ 200 ms** (INP replaced FID in 2024 — if a client's old audit says "FID", it's dated).

Two kinds of truth, both used deliberately:
- **Field data** — real users: PageSpeed Insights' CrUX section (needs traffic), and the **Web performance report inside the Shopify admin**, which shows real-user LCP/CLS/INP. On client work that admin report is your opening evidence and your after-photo; a password-protected dev store has the page but no traffic to fill it.
- **Lab data** — reproducible diagnosis: Lighthouse in devtools (works on localhost and previews), PageSpeed lab runs. Lab finds the *why*; field proves the *so what*.

Sell with field, diagnose with lab, always on mobile throttling.

### The audit method — eight passes

This is the repeatable procedure. Each pass feeds the findings doc:

1. **Baseline:** PSI (field + lab) or devtools Lighthouse on home, product, collection — mobile. Screenshot everything; these are the "before" photos.
2. **Waterfall:** Network tab, disable cache, mobile throttle. Total weight, weight by type, request count, the five biggest files, anything render-blocking.
3. **Images:** oversized (rendered vs intrinsic), lazy-loading discipline, `width`/`height` presence, **identify the LCP element** and judge its treatment.
4. **JS:** Coverage tool for unused %, Performance recording for long tasks, full script inventory from the waterfall.
5. **App attribution:** map every third-party script to its app (domains and paths give them away — extension CDNs, app hostnames). List app embeds if you have admin access; hunt ghost code in the theme (search for app names and orphaned snippet renders).
6. **Fonts:** families × weights, origins, display behavior, preloads.
7. **CLS:** Lighthouse's shift regions + devtools Layout Shift badges — name the shifting elements.
8. **Triage:** every finding tagged **config-level** (compress/replace images, toggle off dead app embeds, trim fonts), **code-level** (LCP preload, lazy discipline, script surgery), or **conversation-level** (remove/replace whole apps, rebuild a bloated section) — then ranked by impact × effort.

### Template 4 — the findings document (`audit-findings.md`)

```markdown
# Performance audit — [store] · [date] · mobile
Baseline: Home LCP __ / CLS __ / INP __ (field|lab) · Product __ · Collection __
Page weight: __ MB, __ requests (product page)

## Top findings (ranked: impact × effort)
1. [Finding] — evidence: [number/screenshot] — fix: [one line] — level: config|code|conversation — est. gain: [High/Med/Low]
2. …

## App inventory & attribution
[app → scripts → weight/cost → verdict: keep / defer / remove-candidate]

## Ghost code found
[what, where, from which departed app]

## Summary for the client (plain language, 4–6 sentences)
[what's slow, why, what we'd do first, what improvement is realistic]
```

That summary paragraph is written for an account manager to forward untouched. **The audit is an engineering document and a sales document in one file** — S1 quotes are built directly from the ranked list.

## 2. Woo bridge

| Your Woo playbook | Here | Verdict |
|---|---|---|
| Hosting/PHP/MySQL tuning, server caching, Redis | Platform-owned | **Dead** — and not missed |
| WP Rocket / page-cache config, cache-exclusion chores | Platform-owned | **Dead** |
| DB cleanup, autoloaded-options audits, transient hygiene | No database access | **Dead** |
| CDN setup, compression, HTTP/2 config | Built in | **Dead** |
| Image discipline (sizing, lazy, formats) | Lever 1 | **Transfers whole** |
| Render-blocking and third-party-script skepticism | Lever 2 | **Transfers whole** |
| Font strategy | Lever 3 | **Transfers whole** |
| Plugin-bloat instinct: inventory → attribute → deactivate-and-test | Lever 4, app edition: inventory → attribute → **app-embed toggles** + remove candidates | **Transfers, renamed** |
| Query Monitor server-side truth | No server access — front-end evidence + Liquid reasoning (a Liquid profiler extension has existed; check its current state before relying on it) | Reduced |
| Asset-unloading plugins (Perfmatters et al.) | No equivalent — manual hygiene | Gone; discipline replaces tooling |

The takeaway: your speed skillset didn't shrink — it **concentrated**. Half the checklist vanished; the surviving half is now the entire job, and you were already good at it.

## 3. Claude Code drill — two audits, one findings doc

Branch: `t3-1-audit`. Deliverable: a real findings document from Template 4.

### Part A — Instruments (~20 min)

On `dawn-playground` via `theme dev`: run devtools Lighthouse (mobile) on home and product. Note the numbers — this is roughly *what clean looks like*, your mental baseline for every audit after. Find where the **Web performance** report lives in your dev store's admin (it'll be empty — know the room anyway; on client work it's your first stop).

### Part B — Pick a real target (~15 min)

Agencies send you a URL before they send you access — the **outside-in audit** is a pre-sale skill, so practice it on a real, public, mid-size Shopify store. Spotting Shopify from outside is its own micro-lesson: assets from the Shopify CDN, `/products/` URLs, `/cart.js` returning JSON. Pick one that's visibly busy — chat bubble, review stars, popups — heaviness is the point. (Public pages, read-only observation: this is exactly what any visitor's browser sees.)

### Part C — The outside-in audit (~90 min, the main event)

Run **all eight passes** on the target — mobile throttled, cache disabled, screenshots as you go. Claude Code is your analysis partner, used precisely:

- Paste the script inventory from your waterfall and ask it to **attribute scripts to apps** — major app signatures (reviews, email/SMS, chat, subscriptions) are recognizable; verify surprising claims with a quick search rather than trusting the guess.
- Paste your Coverage and long-task observations and have it help rank findings by impact × effort — *you* hold the pen on the ranking; it argues, you decide.

No admin access means the app-embed list and ghost-code hunt are inference-only — note them as "verify with access," which is precisely what a real pre-sale audit says.

### Part D — The inside audit (~30 min)

Now audit **your own dev store** with the same eight passes — including your Module 2 work. Eat the dogfood: Is the T2.3 upsell image sized and lazy? Did the T2.2 tabs script defer? Any `width`/`height` missing from things you shipped? Findings about your own code go in the doc too — the review protocol just gained a performance clause, permanently.

### Part E — Write the findings (~45 min)

Produce `audit-findings.md` from Template 4 for the **real store**: baseline numbers, top 5 ranked findings with evidence, app attribution table, triage levels, and the forwardable client summary. Then the retro line: which pass took longest, and what would you template further? Commit doc + template to `notes/`.

**The prescription:** two more outside-in audits this week, different stores, 45 minutes each. By the third, the eight passes run on rails — and you'll have three sample findings docs, which are exactly what gets shown to agencies as proof of the S1 service.
