## 1. Concept

### Metafields — post meta with a type system

A metafield attaches custom data to an existing resource: products, variants, collections, customers, orders, pages, the shop itself, and more. Each is `namespace.key` + a **type** + a value — e.g. `custom.care_instructions`.

**Definitions are the professional standard.** You *can* write ad-hoc metafields via API, but real work starts in **Settings → Custom data**: define the metafield (name, `namespace.key`, type, validations). A definition is what gives you:

- an editing UI on the resource in admin (pin it and it's right on the product page),
- validation at input time,
- and the **⧉ dynamic-source connection** in the theme editor.

**The type catalog** (condensed — same types power metaobject fields):

| Group | Types |
|---|---|
| Text | `single_line_text_field`, `multi_line_text_field`, `rich_text_field` |
| Numbers & logic | `number_integer`, `number_decimal`, `boolean`, `rating`, `money`, `dimension`, `weight`, `volume` |
| Time & misc | `date`, `date_time`, `color`, `url`, `json` |
| References | `file_reference`, `product_reference`, `variant_reference`, `collection_reference`, `page_reference`, `metaobject_reference` |
| Lists | `list.` variant of most of the above — `list.single_line_text_field`, `list.metaobject_reference`, … |

(Shopify also auto-offers **category metafields** from its product taxonomy — standard attributes per product category. Know they exist; apps get their own namespaces too.)

**Liquid access — the `.value` dance.** This is the gotcha zone; learn the rule once:

| You have | Access |
|---|---|
| A metafield | `product.metafields.custom.care.value` — always reach for `.value` |
| A **list** metafield | `.value` *is* the array — loop it |
| A metaobject **entry** | no `.value` on the entry itself |
| A metaobject entry's **field** | `entry.question.value` — fields are metafield-like |

Rich text fields store structured data, not HTML — render them with `| metafield_tag` (semantic HTML) or `| metafield_text` (plain text). And guard everything with `!= blank`: a metafield with no definition, no value, or a draft-status reference renders as nothing — T1.1's silent failure, now with data.

### Metaobjects — custom post types, zero code

A **metaobject definition** is a structure you design (fields from the same type catalog); **entries** are the content. Define in **Settings → Custom data → Metaobjects**; merchants create entries in **Content → Metaobjects**. That's `register_post_type()` plus ACF, as admin configuration.

Capabilities per definition, each a checkbox:
- **Publishable** — entries get active/draft status. In Liquid, a draft entry returns `nil`. Guard accordingly.
- **Translatable** — entries join the store's translation flow.
- **Web pages** — entries get their **own URLs**, rendered by a `metaobject.{type}` template in your theme, which receives a `metaobject` object. Your `single-{cpt}.php`, as a template file.

**Liquid access & the platform's fences (verified, current):**

```liquid
{{ metaobjects.faq['shipping-times'].question.value }}   {% # one entry by handle %}

{% for entry in metaobjects.faq.values %}                {% # all entries of a type %}
  {{ entry.question.value }}
{% endfor %}
```

- By-handle access: max **20 unique handles per page**.
- `values` loops: **50 entries** per loop by default; pagination lifts it to **250 per page**.
- There is **no `meta_query`**. You cannot filter, sort, or search metaobjects arbitrarily in Liquid — you model the data so the access pattern is already the shape you need (references, lists, handles), or you go through the APIs (T5.2).

**One fact that changes client conversations:** definitions and entries live in the **store**, not the theme. Swap themes and the data survives (better than ACF-in-a-theme ever was) — but copy a theme to another store and the code points at definitions that aren't there. Theme code must blank-guard; store setup must be part of delivery scope.

## 2. Woo bridge

| You know (Woo) | Here (Shopify) | Where the mapping breaks |
|---|---|---|
| `get_post_meta()` / stringly-typed meta | Metafields with typed definitions | Validation at input, types at output — `"yes"`-vs-`true` bugs die here |
| ACF field groups (plugin) | Metafield definitions (native admin) | No plugin, no license; the editor UI comes free with the definition |
| `register_post_type()` + ACF | Metaobject definition | No code at all — and it survives theme swaps |
| ACF options page / site-wide fields | Metafields on the **shop** resource | Same idea, first-class |
| ACF relationship / post object | Reference types (`product_reference`, `metaobject_reference`, lists) | Returns the real object in Liquid, not an ID to resolve |
| `single-{cpt}.php` | Web-pages capability + `metaobject.{type}` template | Opt-in per definition |
| `WP_Query` + `meta_query` | **Doesn't exist** | The hard break: model for your access pattern, or use the APIs |
| Meta stored wherever, queried however | 20-handle / 50-loop / 250-paginated fences | The platform trades query freedom for guaranteed performance |

## 3. Claude Code drill — the FAQ feature, two roads

Branch: `git checkout -b t1-5-faq`.

### Part A — Model the data in admin (no code, ~25 min)

1. **Settings → Custom data → Metaobjects → Add definition:** name **FAQ**, fields: `question` (single line text, required), `answer` (rich text), `topic` (single line text). Enable the **publishable** capability.
2. **Content → Metaobjects → FAQ:** create **5 entries** (shipping, returns, sizing — whatever; two sentences each).
3. **Settings → Custom data → Products → Add definition:** name **FAQs**, key `custom.faqs`, type **list.metaobject_reference → FAQ**. Pin it.
4. On **two** products, attach different subsets of your FAQ entries via the pinned field. Leave a third product with none.

You just did the client-facing half of every metaobject build: the data model *is* deliverable design.

### Part B — Road 1, the code road: a global FAQ section

Spec the schema by hand (it's small: heading `inline_richtext`, color scheme, the padding pair), then prompt Claude Code:

> "Create `sections/faq.liquid`. Loop all entries of the `faq` metaobject definition via `metaobjects.faq.values`. Render each as a native `<details>/<summary>` accordion — `summary` holds `question`, the body renders `answer` with the `metafield_tag` filter, no JavaScript. Skip any entry whose question is blank. Use this schema: [paste]. House standards: Dawn padding pattern, color scheme class, `shopify theme check` clean, smallest complete implementation."

Review protocol, with two specific hunts: every field access uses `.value` (or a rendering filter) correctly per the dance table, and blank-guards exist. Add the section to the homepage; confirm all five entries render and open/close with **zero JS** — `<details>` is the honest accordion until T2.2 earns you the scripted kind.

### Part C — Road 1 continued: per-product FAQs

Now the reference metafield pays off. Build `sections/product-faqs.liquid` (largely reuse Part B's markup — consider extracting the accordion into a snippet and `{% render %}`ing it from both sections; that's T1.1 muscle):

- Reads `product.metafields.custom.faqs.value`
- Renders **only** when the list is non-blank — the section should vanish entirely on products without FAQs
- Add it to the product template (below `main-product`)

Verify across your three products: two show *their own* sets, the third shows nothing at all — view source to prove no empty wrapper ships.

### Part D — Road 2, the editor road: dynamic sources (the T1.3 promise)

1. Define one more product metafield: **Tagline**, `custom.tagline`, single line text. Fill it on one product ("Small-batch. Ships in 24h.").
2. In the theme editor, on the product template, pick any stock text setting — the testimonials heading you built, or a Dawn section's text — click the **⧉** icon, and connect it to **Tagline**.
3. Flip between your products in the editor's preview: the connected setting changes per product. Zero code was written.

Then write `notes/metafields-decision.md` — the scoping note you'll reuse for years: **editor road** (dynamic sources into existing settings) when the theme already has the right markup and the merchant should own the mapping; **code road** (sections reading metafields/metaobjects) when you need custom markup, lists, logic, or guaranteed structure. Most client builds use both.

### Part E — Two truths, felt

1. **Draft = nil:** set one FAQ entry to *Draft*. Reload the homepage — it's gone, silently. Reactivate it. That's why every loop guards.
2. **API peek (read-only):** ask Claude Code — toolkit engaged — *"Show me the Admin GraphQL mutation to create an FAQ metaobject entry, and the query to list entries of the definition. Don't run anything."* Read it, recognize the same namespace/key/type vocabulary. That's T5.2 waving from a distance — and proof the definitions you clicked together are ordinary store data behind an API.

**Stretch (optional):** enable the **web pages** capability on FAQ… then realize an FAQ entry doesn't deserve its own URL, and note *that* judgment in the decision file too. (When you meet store-locations or lookbook builds, web pages + a `metaobject.{type}` template is the move — the toolkit will confirm the template wiring when you get there.)
