# T0.3 — Claude Code for Shopify Work
**Module 0 · Tutorial 3 of 26 · Est. 1.5–2 hours**

**Goal:** Configure Claude Code so its Shopify output comes from *current platform docs, not stale training data* — then install the two habits that make AI-assisted work safe to bill for: project rules in `CLAUDE.md`, and a review protocol you run on every change.

**Prerequisites:** T0.1–T0.2 complete. Claude Code installed and signed in — if it isn't, install per the official docs (https://docs.claude.com/en/docs/claude-code/overview, npm package `@anthropic-ai/claude-code`), then come back.

---

## 1. Concept — why AI setup is itself a deliverable

Claude Code will write most of your Liquid from here on. Left unconfigured, that's a liability, for one specific reason: **Shopify moves on a platform cadence** (two Editions per year, API versions retiring quarterly), and the internet — which trained every model — is full of outdated Shopify advice. `checkout.liquid` tutorials, retired REST endpoints, pre-OS 2.0 theme patterns: all of it looks plausible and all of it is wrong now.

The fix is a three-layer setup. Each layer catches what the previous one can't:

1. **Current knowledge** — the Shopify AI Toolkit gives Claude Code live access to shopify.dev docs, API schemas, and validation for GraphQL and Liquid. The model looks things up instead of remembering them.
2. **Project rules** — a `CLAUDE.md` file in the repo root that Claude Code reads automatically. Your standing orders: what it must never do, how it must work, what it must always check.
3. **Your review** — a fixed protocol you run on every AI-assisted change. Layers 1 and 2 raise the quality of what comes out; layer 3 is why it's safe to ship. *The review is the skill.*

One sentence to keep: **AI is the engine, never the autopilot.** Nothing it writes is done until you've reviewed it.

---

## 2. Woo bridge

You may have used AI for WordPress work already. Two things are different here:

**Model memory is more dangerous on Shopify.** WordPress knowledge in AI models is vast and mostly stable — a hook from 2018 usually still works. Shopify knowledge skews stale fast: the platform retires and replaces things on a schedule, and old blog posts outnumber current docs in training data. On Woo, memory was mostly right; here, memory needs a fact-checker. That's what the toolkit is.

**Wrong output fails quietly.** Bad PHP dies loudly — white screen, fatal in `debug.log`. Bad Liquid usually renders *nothing*, silently: a misspelled object just outputs empty. So verification shifts from "run it and read the error" to **validate + inspect**: Theme Check, the toolkit's validation, and your own eyes in the browser.

## 3. Setup — step by step

### Step 1 — Verify Claude Code

```bash
claude --version
claude update   # get current before configuring
```

Then `cd dawn-playground` (your T0.1 theme) — all configuration below is done from inside the project.

### Step 2 — Install the Shopify AI Toolkit (recommended route)

```bash
claude plugin install shopify-ai-toolkit@claude-plugins-official
```

Restart Claude Code after installing. That's it — the plugin runs locally, needs no login or API keys, and **updates itself** as Shopify ships changes.

What it adds: doc search over shopify.dev, API schema lookup/introspection, and validation of GraphQL and Liquid against real Shopify schemas — plus Shopify-specific skills that load automatically when relevant.

**Alternative — the standalone Dev MCP server**, if you prefer plain MCP:

```bash
claude mcp add --transport stdio shopify-dev-mcp -- npx -y @shopify/dev-mcp@latest
```

(Same capabilities at the docs/validation level; the plugin is Shopify's recommended install and bundles more. Either satisfies our build standard. Windows note: if the MCP route errors, the known fix is wrapping the command as `cmd /k npx -y @shopify/dev-mcp@latest`.)

### Step 3 — The litmus test (do not skip)

Open Claude Code in the project and ask these two questions. You're not testing the answers — you're testing **whether it reaches for tools instead of memory**:

1. > "How do I customize the Shopify checkout — is checkout.liquid still the way?"
   A correctly configured setup says checkout.liquid is **retired** and points to Checkout Extensibility. If you get a checkout.liquid tutorial, the toolkit isn't loaded — fix that before continuing.

2. > "Using the Shopify docs, what parameters does the `image_url` Liquid filter accept?"
   Watch the tool calls happen. Docs-backed answer = pass.

If it ever answers a Shopify question from memory when it should look it up, say: *"Check that against the Shopify toolkit/docs first."* The CLAUDE.md below makes that a standing rule.

### Step 4 — Create the project `CLAUDE.md`

Claude Code automatically reads a `CLAUDE.md` at the repo root at the start of every session — it's your permanent briefing to the AI. Create this file in `dawn-playground/` and adapt the marked lines:

```markdown
# Shopify theme project — Dawn playground

## Context
- Shopify theme based on Dawn (Online Store 2.0, JSON templates).
- Dev store: your-store.myshopify.com — development store, test data only.  <!-- EDIT -->
- Developer background: senior WooCommerce/PHP. When a Shopify idiom has no
  WordPress equivalent, explain it briefly.

## Hard rules
- NEVER push to or edit a live/published theme. Work happens through
  `shopify theme dev` or on unpublished themes only.
- Never invent Liquid objects, filters, tags, or schema attributes. Anything
  uncommon gets verified against current Shopify docs (toolkit) before use.
- All user-facing storefront text goes through locale files
  (`locales/en.default.json`) — no hardcoded strings.
- No jQuery. Follow Dawn's existing vanilla-JS / web-component patterns.
- Never modify checkout, analytics, or cart-event scripts without flagging
  it explicitly first.
- Prefer new files (own sections/snippets) over editing Dawn core files.
  If a core edit is unavoidable, keep it minimal and call it out.

## Workflow
- Small diffs. Propose changes file by file and stop for review — do not
  chain multiple features in one pass.
- After any Liquid or schema change, run `shopify theme check` and report
  the result.
- When unsure about current platform behavior, look it up with the Shopify
  toolkit instead of answering from memory.

## Commands
- Dev server: `shopify theme dev --store your-store.myshopify.com`  <!-- EDIT -->
- Lint: `shopify theme check`
```

Commit it — the briefing travels with the repo. On client work, a copy of this file (store URL swapped) is part of project setup.

## 4. Prompting patterns for theme work

Five patterns that separate useful output from plausible junk:

1. **Anchor to exact files.** "In `sections/announcement-bar.liquid`…" beats "in the announcement bar." The model behaves better when it must read the real file first.
2. **State the schema up front.** For anything merchant-editable, specify the settings you want — id, type, label, default — instead of letting the model invent them.
3. **Constrain the finish line.** End prompts with your standards: *"Theme Check clean, strings in locale files, match Dawn's existing patterns, smallest possible diff."* You'll recognize these — they're our QA checklist, moved upstream.
4. **Use your Woo brain as the prompt.** *"In Woo I'd do this with a `woocommerce_before_add_to_cart_button` hook — what's the idiomatic Shopify equivalent here?"* This is your unfair advantage: precise intent, stated in a language you're already fluent in.
5. **Make it teach.** Add *"explain any Liquid idiom you used that differs from PHP templating."* Every task becomes a lesson; this one habit will carry half of Module 1.

## 5. The review protocol

Runs on **every** AI-assisted change — tutorials, drills, and every client delivery to come. No exceptions; speed comes from fluency, never from skipping steps.

- [ ] **Read every changed line.** Could you explain each one to another developer?
- [ ] **Strange = verified.** Any object, filter, tag, or schema attribute you don't recognize gets checked in the docs before it stays.
- [ ] **Diff scope.** Nothing changed outside the files you expected (`git diff` is the truth).
- [ ] **Strings** in locale files, not hardcoded.
- [ ] **`shopify theme check`** — clean.
- [ ] **Behavior verified in the browser** via `theme dev`, including a mobile width.
- [ ] **Committed on a branch** with a message that says what changed and why.

Print it or pin it. By Module 2 it should run in your head in under five minutes.

## 6. Claude Code drill — one real edit, end to end

The task: add an optional **subtext line** to Dawn's announcement bar — a merchant-editable second line under the announcement, hidden when empty.

1. **Branch first** (branch discipline starts now; T7.1 formalizes it):
   ```bash
   git checkout -b t0-3-first-ai-edit
   ```
2. **Start `shopify theme dev`** in a second terminal and keep the preview open.
3. **Prompt** — notice it using all five patterns:
   > "In `sections/announcement-bar.liquid`, add an optional subtext line below the announcement text. Add a schema setting — id `subtext`, type `text`, label 'Subtext', empty default — and render it in a `<p>` only when it's non-empty, styled consistently with Dawn's existing announcement styles. Smallest possible diff, Theme Check clean, follow the section's existing patterns. Explain any Liquid idiom you use that differs from PHP templating."
4. **Watch, then review.** Run the full Section 5 protocol. In particular: open the theme editor (admin → Customize), find the announcement bar, confirm the new *Subtext* field appears, type into it, watch it render — then clear it and confirm the `<p>` disappears entirely from the page source.
5. **Interrogate one thing.** Whatever idiom it explained (`{{ }}` vs `{% %}`, a `default` filter, `unless`…), ask one follow-up question about it. That's T1.1 warming up.
6. **Commit** on the branch with a clear message.

If the output failed any protocol item — good. Tell Claude Code exactly which item failed and why, let it fix it, and re-run the protocol. That correction loop *is* the production workflow.

## Troubleshooting quick hits

- **`claude: command not found`** → Claude Code isn't installed or not on PATH — see https://docs.claude.com/en/docs/claude-code/overview.
- **Plugin install fails** → run `claude update` first; plugin support requires a current Claude Code.
- **MCP route errors on Windows** → wrap the command: `cmd /k npx -y @shopify/dev-mcp@latest`.
- **Toolkit installed but litmus test still answers from memory** → restart Claude Code; then ask the question again with "use the Shopify toolkit" appended once — after that, the CLAUDE.md rule keeps it honest.
