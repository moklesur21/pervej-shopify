# T4.1 — Checkout Extensibility Overview
**Module 4 · Tutorial 16 of 26 · Est. 3–4 hours · Module 4 opens**

**Goal:** Map the checkout world — what replaced `checkout.liquid`, which of the six surfaces handles which kind of ask, what plan gating means for scoping, and where the hard walls are. The drill produces your **checkout translation map**: five real customizations from your Woo history, relocated to their Shopify homes.

**House rule, restated from the catalog:** client checkout work waits until the T4.2 and T4.3 reps are done. Checkout is where the two-regression rule has no mercy.

---

## 1. Concept

### The death of checkout.liquid — and the trade

For years, Plus stores could edit checkout as a Liquid template. That's **fully gone**: `checkout.liquid` was retired in stages through 2024–25, and the last companion mechanism — **Shopify Scripts** — was shut off in **June 2026**, replaced by Functions. Why Shopify killed the open surface: checkout is conversion-critical, PCI-scoped, and evolving fast (Shop Pay, one-page checkout, per-market flows) — arbitrary merchant code meant frozen versions, breakage, and risk. The replacement is the platform thesis you've met all series, at maximum intensity: **sanctioned sockets instead of open surface.** Less freedom, upgrade-safe forever.

### The six surfaces — the new map

1. **Checkout UI extensions** — sandboxed components merchants install at defined points in checkout. The sandbox is strict, by design (straight from the platform's contract): extensions run isolated from the page, **have no access to the real checkout DOM**, can render **only Shopify-provided components** (no arbitrary HTML, no `<script>`), **cannot override CSS** — the merchant's branding always renders — and access to protected customer data requires app-level approval. Two kinds of placement: *static targets* tied to core features (contact info, shipping methods, order summary) and *block targets* the merchant positions in the checkout editor. Tooling note for T4.2: current API versions build on **Polaris web components (Preact-scaffolded)**; React-based extension code is legacy (last supported API version 2025-07) — old tutorials and old AI memories both point at the deprecated flavor.
2. **The checkout editor** — Settings → Checkout → **Customize**. The merchant-facing placement and styling surface: drag extension blocks into position, adjust branding basics. Think theme editor, for checkout.
3. **Checkout branding** — the editor covers logo/colors/type for everyone; the deeper GraphQL **branding API** (fine-grained design tokens) is Plus territory.
4. **Shopify Functions** (T4.3) — the backend logic sockets: discounts, delivery customization, payment customization, cart/checkout validation. Winter '26 gave Functions native read access to app-owned **metaobjects** — merchant-configurable checkout logic, your T1.5 skills pointing at money.
5. **Web pixels** (T5.1) — the sandboxed analytics surface that replaced checkout "additional scripts."
6. **Post-purchase & thank-you / order-status extensions** — the after-payment surfaces: one-click upsell pages, surveys, custom confirmation content.

### The plan question — a scoping checkpoint, not a memory item

Availability is tiered, and it moved recently:

| Surface | Availability |
|---|---|
| Thank-you / order-status / post-purchase extensions | All paid plans (long-standing) |
| Checkout extensibility broadly (per the **Winter '26 expansion** — the announcement reshaping the Plus value proposition) | Opened across paid plans |
| Extensions rendering on the **information / shipping / payment steps** | Shopify's API reference still gates these to **Plus** |
| Branding API (deep tokens) · Scripts-era legacy | Plus · retired |

Read that middle tension carefully: the Winter '26 announcement and Shopify's own API reference don't yet tell one clean story about the deepest checkout steps. Which is exactly why the rule is: **the first question on any checkout job is "what plan is this store on, and which surface does the ask touch?" — verified against current docs that day, via the toolkit.** Plan gating is the single most stale-memory-prone fact in this series; treat every recollection (including this page's) as a hypothesis to check.

### New vs classic customer accounts — the fork you'll get asked about

- **Classic accounts:** the `/account` pages rendered by your theme's `templates/customers/` Liquid — you saw them in T1.2. Password login. Fully themeable, old-world.
- **New customer accounts:** Shopify-hosted, passwordless (email code), Shop-integrated — **not Liquid-themeable.** Customization happens through customer-account UI extensions (same extension model as checkout) and settings; Winter '26 added per-market/B2B account customization. New stores default here, and the order-status experience lives in this world too.

Scoping consequence: *"customize the account area"* forks completely on which mode the store runs — Liquid work in classic, extension/config work in new. Check the mode before quoting; it's one admin glance (Settings → Customer accounts).

### The walls — what's flatly impossible

Say these early and confidently: reordering or restructuring Shopify's checkout steps · arbitrary CSS or DOM surgery on checkout · injecting scripts into checkout pages · custom payment UI outside the sanctioned surfaces (building an actual payment method is a Payments Partner app — a different business, not a theme task). Knowing the walls *is* the expertise; agencies burn weeks discovering them the expensive way.

## 2. Woo bridge — the hook map

The table that retires a decade of muscle memory:

| Woo checkout habit | Shopify home | Notes |
|---|---|---|
| `woocommerce_checkout_fields` — add/remove/modify fields | **UI extension** field components → values saved to cart/order attributes or metafields | T4.2 builds exactly this |
| `woocommerce_before/after_checkout_form`, `review_order` hooks — inject content | **Block targets** placed in the checkout editor | Trust badges, banners, notices |
| `woocommerce_cart_calculate_fees` — add a surcharge | **The honest gap.** Discount Functions adjust *down*, not up; arbitrary fees have no clean socket (workarounds: fee-as-product, shipping-rate shaping) | Say so in scoping — this ask arrives weekly |
| `woocommerce_available_payment_gateways` — hide/show/reorder gateways by condition | **Payment customization Function** | T4.3 |
| Shipping method filtering/renaming/reordering | **Delivery customization Function** | T4.3 |
| `woocommerce_checkout_process` + `wc_add_notice` — validation | **Cart/checkout validation Function** (+ extension-side field validation) | Blocks the buy, server-side |
| `woocommerce_thankyou` — confirmation content | **Thank-you / order-status extension targets** | All plans |
| Tracking via additional scripts / `wp_footer` on checkout | **Web pixels** | T5.1; the old script box is gone |
| Unhook/re-template to reorder checkout | **Wall.** | No socket exists |
| CSS overrides on checkout pages | **Branding** (editor for all; token API on Plus) | Extensions can't touch CSS at all |
| Building a payment gateway plugin | Payments Partner program (an app business) | Refer, don't absorb |

The fundamental break under all rows: in Woo, checkout was *a page in your application* — every byte yours. Here it's **Shopify's product with sockets**. The T0.2 menu-thinking, at its most valuable: senior behavior is hearing an ask and knowing in five seconds whether it's config, an extension, a Function, an app referral — or a wall.

## 3. Claude Code drill — the translation map

No build today; the deliverable is fluency on paper — which is what scoping calls run on. Branch: `t4-1-map` (notes only).

### Part A — Tour the checkout editor (~20 min)

Dev store: **Settings → Checkout → Customize.** Walk it: branding controls, the layout, where extension blocks would slot (the picker is thin until T4.2 gives you an extension to place). Screenshot the surface. Then click everything that *looks* like it should be movable and isn't — feel the walls by hand.

### Part B — Re-walk your own checkout as a buyer (~15 min)

Run the T0.2 test-order path again, but narrating surfaces this time: *that trust-badge slot would be a block target · hiding COD here would be a payment Function · this confirmation page is thank-you-extension territory.* Six surfaces, pointed at, out loud.

### Part C — The artifact: `notes/checkout-translation-map.md` (~60 min)

Take **five checkout customizations you have actually built in Woo** — your real history, not a textbook list (a fee, a field, a gateway condition, a validation rule, a thank-you addition are the usual suspects). For each, five columns:

1. **The Woo build** — hook + one line on what it did
2. **The Shopify home** — which of the six surfaces (or which wall)
3. **Plan requirement** — *verified today via the toolkit*, not recalled; note what the docs said and the date
4. **Verdict** — config / extension / Function / app / not possible
5. **One scoping sentence** — how you'd say it to an agency

Use Claude Code as sparring partner on each mapping, and make it cite current docs for every plan claim — this drill is the toolkit-verification habit at its highest-stakes setting.

### Part D — Three scoping scripts (~20 min)

Write the client-facing answers, three sentences each, ready to say on a call:

1. *"Can we add a gift-message field at checkout?"*
2. *"Can we make checkout match our brand exactly — fonts, layout, everything?"*
3. *"Can we hide Cash on Delivery for orders under 1,000?"*

Each answer names the surface, the plan condition, and the honest limit. These three arrive constantly; having them pre-formed is sales-call muscle.

### Part E — The accounts note (~10 min)

Check which account mode your dev store runs (Settings → Customer accounts), toggle a look at the other, and add a short classic-vs-new scoping note to the map: what "customize the account page" means in each world.

Commit the map and scripts. This document grows for years — every new checkout ask you scope gets a row.
