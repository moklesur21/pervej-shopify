## 1. Concept

### Why pixels exist: the death of script injection

When `checkout.liquid` and its "additional scripts" box died, tracking needed a new home — one that spans the whole funnel *including checkout*, can't break the buy button, and respects consent by construction. The answer is the **Web Pixels** model:

- Pixels run in a **strict sandbox** (isolated from the page — no DOM access, no poking at checkout, no ability to break anything that makes money).
- Instead of scraping pages, they **subscribe to a stream of structured events** the platform publishes:

```js
analytics.subscribe('checkout_completed', (event) => {
  // event.data.checkout — totals, currency, line items, order id…
});
```

- The **standard events** cover the commerce funnel: `page_viewed`, `product_viewed`, `collection_viewed`, `search_submitted`, `product_added_to_cart`, `cart_viewed`, `checkout_started`, the checkout-step events, `payment_info_submitted`, `checkout_completed`. Each carries a rich, structured payload — the data layer you used to assemble by hand, shipped as platform surface.
- **Consent is integrated**: pixels sit behind the Customer Privacy API, so regional consent settings gate what fires. The CMP-plugin duct-tape era doesn't follow you here.

Two kinds of pixel, one decision you'll make on every tracking job:

| | **Custom pixel** | **App pixel** |
|---|---|---|
| Lives | Admin → Settings → **Customer events** → paste JS | An extension in an app (your T4.2 vehicle can carry one) |
| Suits | Store-specific wiring: GA4, GTM, one-off destinations | Versioned, settings-driven, portable across stores |
| Ships | Instantly, merchant-owned, editable in admin | Via `app deploy`, with the version pipeline |

Custom pixel is the default for agency store work; app pixel is the productization path (a tracking setup built three times…).

**The theme ↔ pixel bridge:** theme code can publish its own events into the stream — `Shopify.analytics.publish('upsell_clicked', {…})` — and a pixel subscribes like any other event. That one line is the answer to every *"can we track when customers use our custom thing?"* ask.

### GA4 on Shopify — the honest landscape

- **The blessed path:** the official **Google & YouTube channel app** wires GA4 with the standard ecommerce events, reliably, for free. For a plain "we want GA4" ask, *installing and verifying the official app is the professional answer* — hand-rolling what it does is billing for risk.
- **The custom-pixel path — today's build — earns its keep when** the ask goes beyond plain: GTM in the mix, custom dimensions, additional destinations, custom events, or an agency's measurement spec to implement. You bootstrap `gtag` inside the pixel sandbox and map Shopify events → GA4 ecommerce events (`view_item`, `add_to_cart`, `begin_checkout`, `purchase` with a proper `items` array, `transaction_id`, `value`, `currency`).
- **GTM note:** GTM can load inside a custom pixel and receive dataLayer pushes from your subscriptions — but the sandbox means some tag behaviors differ from open-page GTM. Scope GTM jobs with that sentence in hand.
- **The platform win worth saying out loud:** `checkout_completed` fires once, managed by the platform. The Woo classic — double purchases from thank-you-page reloads, the dedup hacks, the "why is revenue 2×" ticket — is structurally gone.
- **The double-counting rule that replaces it:** one source of truth per destination. Official app *and* a custom pixel both sending `purchase` to the same GA4 property = doubled revenue. Pixel inventory joins your T3.1 audit passes permanently.

### The verification discipline

Tracking deliveries don't ship on "should work." They ship with **evidence**: a full-funnel test (view → add → begin checkout → purchase) watched land in **GA4 DebugView** (and the network tab's `collect` calls), each event checked for its parameters, the purchase checked for correct `transaction_id`, `value`, `currency`, and items — screenshotted into the delivery notes. That's the venture QA line — *"verify events fire through a full test order"* — as a repeatable rep.

## 2. Woo bridge

| You know (Woo) | Here (Shopify) | Where the mapping breaks |
|---|---|---|
| GTM4WP / PixelYourSite / GA plugin stack | Official channel app **or** one custom pixel | The plugin stack collapses into a decision |
| `wp_head` / `wp_footer` script injection, checkout-page hooks | Sandboxed subscriptions — **no page access at all** | You consume a stream; you never touch the page |
| Hand-built `dataLayer` pushes from PHP templates | Structured standard-event payloads | The data layer is platform surface now |
| Thank-you-page double-purchase bug + dedup hacks | `checkout_completed`, platform-managed, fires once | A whole bug genre retired |
| Consent via CMP plugins wired to tags | Customer Privacy API, integrated | Consent is substrate, not bolt-on |
| Custom event tracking via inline `gtag()` calls in templates | `Shopify.analytics.publish` → subscribe | One clean bridge, checkout-safe |
| Server-side tracking plugins (Measurement Protocol) | Webhook-driven middleware — **T5.2's territory** | Forward pointer, not today's build |
| Tag Assistant / DebugView habits | Identical | Transfers whole — your verification muscle is already trained |

## 3. Claude Code drill — observe, map, wire, verify

Branch `t5-1-tracking` in the theme repo for notes + the theme-side bridge; the pixel itself lives in admin.

### Part A — The debug pixel: see the stream first (~40 min)

Before wiring any destination, watch the raw events — this is `| json` for the tracking layer:

1. Admin → Settings → **Customer events** → Add custom pixel → `debug-pixel`. Code: subscribe broadly (the catch-all subscription, or the standard set individually) and log event name + full payload to the console.
2. Connect it, then walk the funnel on the storefront with the console open: product page → add to cart → cart → checkout → **complete a test order.** Watch every event arrive; expand the payloads.
3. Record reality in `notes/pixel-events.md`: each funnel event and the **actual payload paths** you'll need — where the price lives on `product_viewed`, where totals, currency, and line items live on `checkout_completed`. *Written from observation, not from memory or model recall* — payload paths are exactly the kind of detail that drifts, and your Part B map will be built from this file.

### Part B — The GA4 custom pixel, spec-first (~75 min)

1. **Hand-write the event map** — the deliverable of every tracking job, and the thing agencies actually pay for:

| Shopify event | GA4 event | Params (← path from Part A notes) |
|---|---|---|
| product_viewed | view_item | currency, value, items[] |
| product_added_to_cart | add_to_cart | … |
| checkout_started | begin_checkout | … |
| checkout_completed | **purchase** | transaction_id, value, currency, items[] |

2. Master prompt: your map + Part A's payload notes + *"gtag bootstrapped inside the pixel sandbox with my measurement ID and debug_mode; build each GA4 event strictly from the mapped payload paths; currency and value always from the payload, never hardcoded; no DOM access; fail silently if a path is missing."*
3. Review hunts: every path matches your **observed** notes (invented paths are the #1 AI failure here) · `items[]` assembled correctly from line data · nothing reaches for `document`/`window` page access · the map and the code agree exactly.
4. Replace or disable the debug pixel's noise if it distracts; keep it around — it's a permanent diagnostic tool.

### Part C — The verification rep (~45 min, the core skill)

GA4 **DebugView** open in one window, storefront in another, network tab filtered to `collect`:

Walk the full funnel and verify **each** event as it lands — name, params, values. Then the test order, then the moment that matters: **`purchase` arrives exactly once**, with the right `transaction_id`, `value`, `currency`, and items. Screenshot each landing. Assemble the evidence trail into `delivery-notes.md` (Template 3, tracking edition) — this evidence format *is* how S4 tracking work gets handed off.

### Part D — The theme ↔ pixel bridge (~30 min)

Client-shaped ask: *"track when the cart-drawer upsell gets used."*

1. In the T2.3 upsell's theme JS path, publish `upsell_clicked` via `Shopify.analytics.publish` with product id + price from the page context.
2. Subscribe in your pixel → forward as a GA4 custom event.
3. Click the upsell, watch it land in DebugView. One custom feature, measurably used — add the pattern to your notes; the ask recurs constantly.

### Part E — The audit habits (~20 min)

Write `notes/tracking-audit.md`:

- **Double-count detection:** what two `purchase` events per order look like in DebugView, and the one-source-of-truth rule per destination.
- **Pixel inventory joins the T3.1 audit:** Settings → Customer events is now a standard stop — every pixel attributed, duplicates flagged, ghosts (departed apps' pixels) hunted.
- **The decision note:** official app for plain GA4 · custom pixel for GTM/custom/spec work · app pixel when it's productized. Three lines you'll reuse in scoping weekly.

*(Stretch, 15 min: `shopify app generate extension` → web pixel in the T4.2 lab app — read the scaffold, don't build. Knowing the app-pixel shape exists is enough until a client needs one.)*

## 4. Verification checklist

- [ ] Debug pixel live; full funnel observed; `notes/pixel-events.md` written **from observed payloads**
- [ ] Event map hand-written before any pixel code; GA4 pixel built strictly from it
- [ ] Review passed: no invented payload paths, no hardcoded currency/value, no page access
- [ ] Full-funnel DebugView verification complete — every event, every param, screenshotted
- [ ] `purchase` landed **exactly once** on a completed test order, values correct
- [ ] Custom event bridged from the T2.3 upsell and verified in DebugView
- [ ] Evidence trail assembled into delivery notes — the S4 handoff format
- [ ] `tracking-audit.md` written: double-count rule, pixel-inventory audit stop, the three-line decision note
