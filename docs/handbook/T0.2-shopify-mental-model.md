# T0.2 — The Shopify Mental Model for Woo Devs
**Module 0 · Tutorial 2 of 26 · Est. 2–3 hours**

**Goal:** Rewire the instincts. By the end, when you hear a client request, your first question is no longer *"which hook do I use?"* but *"which extension surface does this belong to?"* — and you can move around the Shopify admin as comfortably as wp-admin.

**Prerequisites:** T0.1 complete (dev store exists, you can log into its admin, your practice theme is pushed).

---

## 1. Concept — you're not administering a stack anymore

WordPress hands you a server and says *"run anything."* Shopify hands you a platform and says *"extend at these points."*

On Woo, your expertise was knowing how to build anything, because anything was possible with enough PHP. On Shopify, your expertise is knowing **the menu of sanctioned extension points** — which one fits a request, and when a request isn't on the menu at all. Saying "that's not possible on this platform, here's the nearest thing that is" early and confidently is senior behavior, and it's part of what agencies pay for.

**The five questions that change:**

| In Woo you asked… | On Shopify you ask… |
|---|---|
| "How do I code this?" | "Which extension surface allows this?" |
| "Which hook fires here?" | "Is there a Function API, webhook, or setting for this?" |
| "What's in the database?" | "What does the API expose?" |
| "Which plugin does this?" | "Native feature, theme code, Function, or app — and what's the speed cost?" |
| "How do I keep it update-safe?" | Same worry, new answer: settings, metafields, and your own sections — not child themes |

**The extension surface map** — the decision framework for every client request from now on:

```
Client asks for X
│
├─ Storefront look or behavior?         → THEME (Liquid + CSS + JS)          [Modules 1–3]
├─ Merchant-editable content/data?      → SECTION SETTINGS · METAFIELDS ·
│                                          METAOBJECTS                       [T1.3, T1.5]
├─ Discount / shipping / payment /
│  validation logic?                    → SHOPIFY FUNCTIONS                  [T4.3]
├─ Anything inside checkout UI?         → CHECKOUT UI EXTENSION
│                                          (never theme code)               [T4.2]
├─ Sync, automation, external systems?  → APP: your server + APIs + WEBHOOKS [T5.2–5.3]
└─ None of the above?                   → Possibly not possible. Check, then
                                           say so — early and plainly.
```

Print this. Every tutorial from here on fills in one branch.

## 2. Woo bridge — the full remapping

### 2.1 The stack

| You managed (Woo) | Who manages it now |
|---|---|
| Hosting, PHP versions, MySQL, SSL, CDN | Shopify |
| Security patching, backups, uptime, scaling | Shopify |
| Cron jobs | Don't exist — apps schedule their own work; Shopify Flow automates in-admin |
| Transactional email delivery | Shopify (templates editable in admin) |

You will never patch, back up, or migrate a server again for Shopify clients. You also can never touch one.

### 2.2 Where code runs — the single biggest retraining

On Woo, your PHP executed **inside** the site on every request and could intercept anything.

On Shopify, your code runs in exactly three places:

1. **Shopify's servers render your Liquid.** Templates, not programs — no arbitrary code, no DB calls, deliberately limited (T1.1).
2. **The browser runs your JavaScript.** Theme JS is where storefront interactivity lives (T2.2).
3. **Your own infrastructure runs app code**, talking to the store via APIs and webhooks (T5.2).

Plus one special case: **Shopify Functions** — compiled logic Shopify runs for you, but *only* at specific decision points it has opened up (discounts, shipping, payment customization, cart validation…). The closest thing to a filter you'll get — but only where Shopify installed the socket.

There is no `functions.php`. There is no "just add a filter." When you feel that reflex, come back to the map in Section 1.

### 2.3 Events: hooks vs webhooks

- **Woo hooks** were synchronous and in-process: they could *change the outcome* before it happened.
- **Shopify webhooks** are async HTTP POSTs to your server *after the fact*: you can **react**, never intercept.
- The only interception points are **Functions** — roughly a dozen sanctioned ones, not thousands of hooks.

Habit that breaks hardest: *"I'll filter the price at runtime."* Prices change via API writes, discount Functions, or B2B price lists — never by intercepting a page render.

### 2.4 Data: from `$wpdb` to APIs

| Woo | Shopify |
|---|---|
| `wp_posts` + `wp_postmeta`, direct SQL anytime | Resources behind the **Admin GraphQL API** — you never see a database |
| REST API as the modern interface | **GraphQL is primary**; the REST Admin API is legacy. When Claude Code suggests old REST snippets, that's your cue to redirect it (T0.3 fixes this at the source) |
| Post meta (stringly-typed, anything goes) | **Metafields** — typed, with definitions and validation. Genuinely nicer |
| Custom post types | **Metaobjects** (T1.5) |
| Bulk = raw SQL or WP-CLI | Bulk = GraphQL bulk operations |

### 2.5 The product model — study this one properly

- **Woo:** product = post; attributes → variations; simple/variable/grouped/external types.
- **Shopify:** product → **options** (max **3** per product: e.g. Size, Color, Material) → **variants** (each combination). Limit: **2,048 variants per product** (raised from the long-standing 100 in Oct 2025 — but the 3-option cap did *not* change).
- No grouped/external product types — those patterns are built differently here (bundles, apps, line-item properties).
- **Inventory is first-class:** locations, per-location stock levels — not a meta field bolted on.

The 3-option cap is the wall Woo devs hit first ("client needs Size + Color + Material + *Fit*"). Workarounds exist (combined option values, splitting products, apps) — knowing the wall exists is today's job.

### 2.6 Taxonomy & content

- Categories/tags → **collections**: *manual* (hand-picked) and *automated* (rule-based — a tax query you define in the admin, forever self-updating) + free-form tags.
- WordPress-the-CMS → Pages and Blogs exist but are basic. Structured content lives in **metaobjects**. WordPress is the better CMS; this is a commerce platform with a CMS attached, not the reverse — and that's fine.

### 2.7 People

WP users with roles/capabilities → two entirely separate systems: **Customers** (storefront accounts — T4.1 covers new vs classic) and **Staff** (admin access). They never mix.

### 2.8 Themes & apps (T0.1 recap, deepened)

- Child theme → **full theme copy**; updates are manual merges. So "update-safe" now means: your code in your *own* sections/snippets/blocks, merchant data in settings and metafields, minimal edits to the theme's core files. Same instinct as "never hack the parent theme," different mechanics.
- Plugin (in-process PHP, can do anything) → **app** (external service that injects UI through defined slots: app blocks, app embeds, checkout extensions). Apps add weight through injected scripts — **app bloat is a speed factor you will later bill agencies to fix** (Module 3).

### 2.9 Phrases to retrain

- "Let me check the database" → *"Let me query the API."*
- "I'll hook into checkout" → *"Checkout UI extension or Function — which?"*
- "Install a plugin for that" → *"Is it native? If not, which app — and what does it cost in scripts?"*
- "I'll fix it in functions.php" → *"There is no functions.php. Which surface?"*

## 3. Guided admin tour — hands-on (~45 min)

Do this in your dev store admin, in order. Exact menu wording drifts between admin versions; the destinations don't.

**Stop 1 — Orientation.** Walk the left rail top to bottom once. Rough equivalents: Orders ≈ WooCommerce → Orders · Products ≈ Products · Customers ≈ Users (customers only) · Content ≈ a thin wp-admin content area (note **Metaobjects** in here — T1.5) · Analytics ≈ built-in reports · Online Store ≈ Appearance + storefront settings · Settings ≈ WooCommerce → Settings.

**Stop 2 — Create a product by hand.** Title, description, a couple of free images. Add **2 options** — Size (S/M/L) and Color (Black/White) — and watch Shopify generate the **6 variants**. Set prices, SKUs, and inventory at your location. Feel how different this flow is from Woo's attributes → variations dance.

**Stop 3 — Collections.** Create **one manual** collection and **one automated** collection with the rule *product tag equals `sale`*. Then tag your product `sale` and watch it appear in the automated collection on its own. That's a tax query defined in admin — merchants can do this without you, which changes what clients ask developers for.

**Stop 4 — Enable the test payment gateway.** Settings → Payments → activate the test provider — **Bogus Gateway** (search "bogus" if you don't see it) or Shopify Payments test mode if offered. Dev stores can only ever take test orders.

**Stop 5 — Place a test order like a customer.** Open the storefront (if the password page appears, the password is under Online Store → Preferences). Add your product to the cart → check out → pay with the Bogus Gateway: card number `1`, any name, expiry, CVV.
Worth memorizing for QA later: card `1` = success · `2` = declined · `3` = gateway error.

**Stop 6 — Orders.** Find your order. Open it: timeline, fulfillment, restock/refund. **Refund it fully** to see that flow too. You just performed our QA checklist item *"full purchase flow test"* for the first time — it runs on every delivery from here to forever.

**Stop 7 — The theme editor.** Online Store → Themes → your T0.1 theme → **Customize**. This is the merchant's world — and unlike the Customizer's side-role in Woo, it's the *primary interface your work will serve*. Add a section to the homepage, reorder it, delete it. What you can offer merchants **here** is exactly what T1.3 teaches you to build.

**Stop 8 — Apps.** Open the Shopify App Store and read one popular free app's listing *like a skeptic*: what surfaces does it touch? Do reviews mention speed? **Don't install anything today** — evaluation discipline comes in T5.3.

## 4. Claude Code drill

**Drill A — Build the map yourself, then let AI attack it.**
1. **Without AI:** from T0.1 plus today's tour, write `woo-to-shopify-map.md` — minimum **12 rows**, three columns: *Woo concept · Shopify equivalent · where the mapping breaks*.
2. **Then** open Claude Code and ask:
   > "Here's my WooCommerce → Shopify mental-model mapping. Mark anything wrong, anything oversimplified, and add up to 5 rows I'm missing."
3. Pick **one** of its corrections and verify it against Shopify's docs before accepting it.

The order is the point: your understanding first, AI as reviewer second. That's the muscle.

**Drill B — Translate your own past work.**
Pick **3 real things you've built in Woo** — a checkout tweak, a My Account addition, a pricing rule, a custom email, whatever's actually in your history. For each, ask Claude Code:
> "On Shopify, which extension surface would this need — theme code, section settings, metafields, a Function, a checkout UI extension, or an app — and why?"

Then place each one on the Section 1 map **yourself** and note whether you agree. Write down any disagreement — the series will settle each one as we reach that surface.

Keep both files in your training folder. Drill B's list becomes a personal progress marker: by Module 7 you should be able to build all three.

## 6. Done when

Every box ticked **and** you can answer these out loud, without looking:

1. Name the three places your code can run on Shopify — and the one place it never will.
2. Why can a webhook never *change* an order, and what's the only mechanism that can intercept platform behavior?
3. A client wants free shipping over $100, but only for approved wholesale customers — which surface(s) would you reach for? *(Sketch it now; T4.3 and T6.1 will confirm. The win is reaching for the map, not for hooks.)*
