# T2.2 — Theme JavaScript Done Right
**Module 2 · Tutorial 11 of 26 · Est. 4–5 hours**

**Goal:** Write storefront JavaScript the way Dawn does — self-initializing web components, zero jQuery, zero libraries — that survives the theme editor, respects accessibility, and **never breaks the scripts that make the store money**. The drill ships an accessible tabbed-content component.

**Prerequisites:** T2.1 method installed. Your T1.5 `<details>` accordion was the zero-JS baseline; today you earn the scripted kind.

---

## 1. Concept

### The philosophy: Liquid renders, JavaScript enhances

In this world the server (Liquid) produces complete, readable HTML; JS adds behavior on top. If your JS fails to load, the content must still be *usable* — maybe uglier, never gone. This isn't idealism: it's why Dawn scores what it scores, and it's the standard agencies believe they're buying when they buy "senior."

Practical corollary — **the no-JS ladder**. Before writing a component, walk down:
1. Can CSS do it? (hover states, `:focus-within` menus, `scroll-snap` for simple sliders)
2. Can native HTML do it? (`<details>` — you've shipped this)
3. OK — now a *small* component. No Swiper, no Slick, no external libraries, ever (T1.6 doctrine, both themes).

### The pattern: custom elements

Dawn's JS is built from **web components** — custom elements that hydrate server-rendered markup:

```js
class TabbedContent extends HTMLElement {
  connectedCallback() {
    // element is in the DOM — find children, wire listeners
  }
  disconnectedCallback() {
    // remove any document/window-level listeners you added
  }
}
customElements.define('tabbed-content', TabbedContent);
```

```liquid
<tabbed-content class="…">
  …server-rendered tabs markup…
</tabbed-content>
<script src="{{ 'tabbed-content.js' | asset_url }}" defer="defer"></script>
```

Why this pattern owns the theme world:

- **Self-initializing.** No `DOMContentLoaded` + `querySelectorAll` soup; the browser calls `connectedCallback` for every instance, including ones added *later*.
- **Editor-proof.** The theme editor re-renders sections without a page load. Re-inserted markup re-triggers `connectedCallback` — your component just works, where listener-soup code silently dies. This is the killer argument.
- **Naturally scoped.** `this.querySelector(...)` looks inside the component. Multiple instances coexist for free — the same discipline as your `section.id` CSS scoping.

**Where JS lives:** one asset file per component, `<script … defer>` **inside the section that needs it** — pages without the section never pay for it. (Liquid de-duplicates repeated asset tags; a `{% javascript %}` tag also exists, but per-component asset files are the house standard, matching Dawn.)

### Talking to the editor

The editor fires document-level events as merchants work: `shopify:section:load`, `shopify:section:select`, `shopify:block:select` (and their `deselect`/`unload`/`reorder` siblings). Two professional uses:

- Components built as custom elements rarely need `section:load` — re-insertion handles them. Listener-soup code needs it as a crutch; prefer not to need crutches.
- **Delight move:** listen for `shopify:block:select` and reveal the block being edited (activate that tab, scroll that slide). Guard editor-only code with `if (Shopify.designMode)`. Dawn does this for slideshows; merchants notice.

Document-level listeners are exactly what `disconnectedCallback` exists to clean up.

### Passing Liquid data to JS

No `wp_localize_script` here. Two patterns:

```liquid
{% # scalars → data attributes %}
<tabbed-content data-remember="{{ section.settings.remember_tab }}">

{% # structures → a JSON script block %}
<script type="application/json" data-tab-config>
  {{ some_object | json }}
</script>
```

Read with `this.dataset.remember` / `JSON.parse(this.querySelector('[data-tab-config]').textContent)`. Never build JS string literals by interpolating Liquid into code.

### The never-break rules

The QA checklist line — *"cart/checkout scripts unbroken (analytics, upsells, shipping calc still fire)"* — exists because themes share the page with apps, pixels, and platform scripts. Your standing rules:

1. **No global click/submit handlers** that `preventDefault()` or `stopPropagation()` outside your own component's root.
2. **Never remove, wrap, or rename** the product form, its inputs, or platform script tags — other scripts hook them by name and id.
3. **No globals leaked**, no monkey-patching `window.Shopify` or `fetch`.
4. When you *extend* cart behavior (T2.3), use the theme's existing event bus (Dawn ships a small `pubsub.js`) instead of inventing signals apps can't hear.
5. After any JS work: run the coexistence check — the full add-to-cart flow still works, console clean.

### Accessibility is in scope, always

An interactive component without keyboard support is a defect, not a nice-to-have. Today's tabs follow the standard ARIA pattern: `role="tablist"/"tab"/"tabpanel"`, `aria-selected`, `aria-controls`/`aria-labelledby`, roving `tabindex`, and Arrow/Home/End keyboard navigation. Dawn is an accessibility benchmark; deliveries under our name match it.

## 2. Woo bridge

| You know (Woo) | Here (Shopify) | Where the mapping breaks |
|---|---|---|
| jQuery ships with WP; `$(document).ready()` culture | No jQuery. Vanilla + custom elements | `$` isn't there — and nothing misses it: `querySelector`, `classList`, `dataset`, `fetch`, `addEventListener` cover the old habits |
| `wp_enqueue_script` + conditional `is_page()` logic | `asset_url` + `defer` inside the section | Loading is conditional *by usage*, automatically |
| jQuery plugins (Slick, Fancybox…) | Forbidden | Native patterns + small components; `scroll-snap` before any slider script |
| `wp_localize_script` | data attributes / JSON script blocks | Same job, no PHP bridge |
| Customizer selective-refresh JS handlers | Editor events + custom elements | The re-render problem you fought in the Customizer is solved *structurally* by `connectedCallback` |
| Plugin script conflicts | App + pixel + theme script conflicts | Same war, new actors — the never-break rules are your side of the treaty |
| Cart fragments JS | Cart API + theme pub/sub | Next tutorial's whole subject |

## 3. Claude Code drill — accessible tabs, end to end

Client-shaped brief: *"Tabbed content section — e.g. Description / Shipping / Care — merchant-managed tabs."* Branch: `t2-2-tabs`.

### Part A — Read Dawn's JS first (~30 min)

Open `assets/global.js` plus one or two standalone components — `cart-drawer.js`, `details-disclosure.js` (names vary slightly by Dawn version). Have Claude Code annotate one:

> "Explain this component class: lifecycle, what it queries, what it listens to, how it would behave if the section were re-rendered by the theme editor. I know PHP/jQuery-era patterns; contrast where useful."

Then distill `notes/js-component-skeleton.md` — *your* house skeleton: class shape, `connectedCallback` wiring, `disconnectedCallback` cleanup, no globals, data-attribute config. This skeleton rides along in every future JS prompt, exactly like the schema rides along in section prompts.

### Part B — Spec by hand: schema + behavior

Schema (fast for you now): heading, color scheme, padding pair; block type `tab` (max 6): title (`text`), content (`richtext`).

**Behavior spec** — the new muscle; you can't review JS without having decided what correct means:

- Click a tab → its panel shows, others hide; `aria-selected` and roving `tabindex` update.
- Keyboard: Left/Right arrows move between tabs (wrapping), Home/End jump, panel is focusable.
- **Progressive enhancement via `:defined`:** server renders all panels visible with their titles as headings — fully readable with no JS. CSS scoped to `tabbed-content:defined` switches on tab presentation; if the script never loads, the section degrades to stacked content, not to broken tabs.
- **Editor:** in design mode, `shopify:block:select` activates the selected tab; listener added in `connectedCallback`, removed in `disconnectedCallback`, guarded by `Shopify.designMode`.
- Config example: a `remember_tab` checkbox setting → data attribute → last active tab index in `sessionStorage`.

### Part C — Build

Master-prompt style, JS edition: your schema + behavior spec + the Part-A skeleton + house standards ("no libraries, defer, no globals, listeners cleaned up, Theme Check clean, list anything you couldn't implement"). Review protocol with the JS extensions — hunt specifically for:

- any listener on `document`/`window` without a matching cleanup
- any `preventDefault` that could reach beyond the component
- ARIA attributes actually updating on interaction (inspect, don't assume)
- the `:defined` CSS really present and scoped

### Part D — The four proofs

1. **No-JS proof:** disable JavaScript in devtools → reload → content stacked and readable. Re-enable.
2. **Editor proof:** change a section setting (forces re-render) → tabs still work. Click tab blocks in the sidebar → the matching tab activates.
3. **Coexistence proof:** add the section to the product template above `main-product` → full add-to-cart flow with a test order-start → works, console clean. Remove the section after if you like — the *proof* is the habit.
4. **Keyboard proof:** unplug the mouse (spiritually): Tab into the tablist, arrow through, Home/End, into the panel. No traps, visible focus.

### Part E — Close the loop

`notes/js-review-additions.md`: the JS-specific review items from Part C, appended to your T0.3 protocol — this is now the protocol for every scripted deliverable. Commit component, section, notes.
