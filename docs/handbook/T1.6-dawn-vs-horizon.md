# T1.6 — Dawn vs Horizon
**Module 1 · Tutorial 9 of 26 · Est. 3–4 hours · Closes Module 1**

**Goal:** Become bilingual. Dawn and Horizon are the two architectures your client work will land on — you'll learn what actually differs, build the same section in both, and leave with the decision framework agencies will pay you to have: *which theme, when, and is a migration worth it?*

**Prerequisites:** T1.1–T1.5 complete. Everything in Module 1 gets used today.

---

## 1. Concept — one platform, two generations

| | **Dawn** | **Horizon** |
|---|---|---|
| Born | 2021 — the OS 2.0 reference theme | May 2025 (Summer Editions) — **default for new stores since** |
| Architecture | Sections + **section-local blocks** (T1.3), flat | **Nested theme blocks** (T1.4), 8 levels — sections are thin hosts |
| Family | One theme | **Ten themes, one architecture**: Horizon, Fabric, Ritual, Vessel, Heritage, Tinker, Savor, Dwell, Atelier, Pitch — all free |
| JavaScript | Vanilla web components, no framework, no jQuery | Web components too — core pieces (variant picker, gallery, cart drawer) partly behind **Shadow DOM** |
| CSS | `base.css` + per-component asset files, CSS custom properties | Custom properties as well; leans harder into animation/transitions; block CSS scoped inline |
| Editor | Functional, stable, essentially the 2021 editor refined | Much more capable: deep nesting, **AI block generation** (Sidekick/Magic) |
| Status | **No deprecation announced** — still updated, long-term support signaled | The flagship Shopify is actively building on |
| Installed base | Enormous — most 2021–2025 client themes are Dawn or Dawn-shaped | Growing — every new store, every redesign |

Facts under the table that shape client work — all current as of this writing:

- **Performance honesty.** Third-party benchmarks in 2026 consistently show default Horizon trailing default Dawn on *mobile* PageSpeed by a wide margin (roughly 30 points in some tests; desktop is at parity), with the gap narrowing on well-optimized real stores. Dawn remains the lighter, more forgiving base. Remember this for Module 3 — "we moved to the new theme and got slower" will be a ticket you receive.
- **No migration path.** There is no automatic Dawn → Horizon conversion. Moving is a **rebuild** — typically tens of hours for a moderately customized store — because the block models don't translate.
- **Updates overwrite.** Horizon updates frequently, and updates have a track record of clobbering direct customizations. Our duplicate-the-theme rule and own-files discipline aren't just house style on Horizon — they're survival.
- **App compatibility gotcha.** Some older apps integrate by poking at theme DOM; Horizon's Shadow-DOM-wrapped components break those patterns. On Horizon projects, app compatibility is a scoping question, not an assumption.
- **AI blocks are scaffolds.** Merchants can generate theme blocks in the editor. Reviews match our doctrine exactly: impressive on simple blocks, unreliable on complex ones — generated code gets the same line-by-line review as any other AI output, because it *is* any other AI output.

### What Horizon changes for you, the developer

1. **Sections get thin; blocks get real.** "Build a section" often becomes "compose stock blocks, write one custom block for the gap." Less Liquid written, more architecture decided.
2. **Block CSS scoping convention:** derive a unique ID from `block.id`, wrap styles in a `{% style %}` tag with every selector prefixed by it — encapsulation without Shadow DOM, safe across multiple instances. (Your T1.3 `section.id` habit, one level down.)
3. **No external UI libraries.** No Swiper, no Slick. Interactivity = small vanilla web components, ideally initialized only when visible (`IntersectionObserver`). This is also Dawn doctrine — Horizon just enforces the culture harder.
4. **Template JSON gets big.** Nesting means a hero that was 20 lines of JSON in Dawn can be 60+ in Horizon. Diffs are noisier; the T1.2 pull-diff-decide habit earns its keep.

### The 60-second architecture detection (client-repo onboarding skill)

Before touching any client theme, answer *which world is this?*

1. `/blocks` folder present **and populated**? → theme-block world.
2. Sections containing `{% content_for 'blocks' %}` and schemas with `"@theme"`? → theme-block world.
3. Schemas defining their own `blocks` arrays with settings? → section-block world (Dawn-shaped).
4. Mixed across the theme? Fine — but per section it's one or the other (T1.4's law).

**House rule: match the architecture you find.** Consistency beats preference on client work; your preference only gets a vote on greenfield builds.

## 2. Woo bridge

You have lived this exact transition once already:

| WordPress history | Shopify present | The rhyme |
|---|---|---|
| Classic themes (template hierarchy, PHP parts) | Dawn (sections + local blocks) | The refined old world with the massive installed base |
| Block themes / FSE | Horizon (nested theme blocks) | The composable new world, default for new builds |
| "The money is in the installed base" | Most billable work is on Dawn-shaped themes | New-build work adopts the new architecture; rescue/feature work lives on the old one — be bilingual |
| FSE's rocky early reviews | Horizon's editor power + stability complaints | History rhyming in real time; judge by version, not by launch memory |
| "Updates overwrite core edits" | Horizon updates clobbering customizations | Same lesson, same defense: own files, duplicated themes |
| `theme.json` design tokens | CSS custom properties + settings schema | Same instinct, different syntax |

Where the rhyme breaks, pleasantly: **one vendor, ten skins, one architecture.** Learn Horizon once and you've learned Fabric, Ritual, Vessel and the rest — there is no thousand-theme fragmentation problem to fight.

## 3. Claude Code drill — the same section, twice

The build: a **feature-highlights strip** — 3–4 items, each an icon/image, a title, and one line of text. Small enough to finish twice, real enough to expose the architectural difference.

### Part A — Scaffold Horizon and tour it (~30 min)

```bash
cd ..   # out of dawn-playground
shopify theme init horizon-playground
```

Pick **Horizon** when asked (fallback: `--clone-url https://github.com/Shopify/horizon`). Git-init it, baseline commit, `shopify theme dev` against the same dev store.

Tour with intent, `notes/architecture-detection.md` open as you go:
- Diff the folder trees mentally: `/blocks` is *full* here.
- Open one section in each theme side by side — feel the thickness difference; find `{% content_for 'blocks' %}` in the Horizon one.
- Skim two stock Horizon blocks; find the unique-ID + `{% style %}` scoping pattern in the wild.
- Finish the detection checklist in your own words.

### Part B — Build it in Dawn (~30 min, fluency check)

Section + local blocks, the T1.3 way: spec the schema by hand, AI builds, full review protocol. This should feel *fast* now — that speed is Module 1 working.

### Part C — Build it in Horizon, two passes

**Pass 1 — no code.** In the Horizon editor, compose the same UI from **stock blocks only** (group/row + image + text). Time yourself. Note what you couldn't match — spacing? icon treatment? That gap is your spec.

**Pass 2 — one custom block.** Build `blocks/highlight.liquid` to close the gap, to Horizon conventions:

> "Create `blocks/highlight.liquid` for this Horizon-based theme: settings for image (`image_picker`), title (`text`), and text (`inline_richtext`). Follow this theme's existing block conventions — check current Horizon/theme-block docs with the Shopify toolkit rather than assuming. Scope all CSS with a unique ID derived from `block.id` inside a `{% style %}` tag. Default wrapper unless the markup requires `tag: null` — if so, say why. Preset required. No external libraries. Theme Check clean."

Review with extra suspicion — **Horizon conventions are the newest surface in this series, exactly where AI training data is thinnest, so the toolkit lookup is least optional here.** Then compose 3–4 Highlights inside a stock section accepting `@theme`, next to your Pass-1 attempt.

### Part D — The comparison that becomes consulting material

Write `notes/dawn-vs-horizon.md` from evidence you just generated:

- Lines of Liquid/JSON you *wrote* in each vs what you *configured*
- Time to done, both routes
- What the merchant can change afterward in each — and what they can break
- Quick Lighthouse run on both playground homepages (default content) — record mobile scores; you're foreshadowing Module 3, not auditing yet
- Your migration rubric, in your own words: **new build or full redesign → Horizon · healthy, tuned, converting Dawn store → stay · messy Dawn fork with a merchandising team blocked on devs → rebuild case, quoted as a rebuild**

Commit both repos. That note is a real answer to a real agency question — you now hold it with evidence, not opinion.
