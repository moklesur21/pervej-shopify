## 1. Concept — a section is markup plus a contract with the editor

A section is one `.liquid` file with two halves:

```liquid
{% comment %} markup half — renders on the storefront {% endcomment %}
<div class="testimonials section-{{ section.id }}-padding">
  <h2>{{ section.settings.heading }}</h2>
  {% for block in section.blocks %}
    <figure {{ block.shopify_attributes }}> … </figure>
  {% endfor %}
</div>

{% schema %}
{ …the contract half — what the merchant can edit… }
{% endschema %}
```

The `{% schema %}` JSON is a **declaration to the theme editor**: this section's name, its settings, its blocks, whether it can be added freely. Values come back to you as `section.settings.<id>` and `block.settings.<id>` — and are stored per instance in the template JSON, exactly where T1.2 showed you the merchant writes.

### The schema, part by part

**`settings`** — the merchant's controls. The platform gives you a fixed catalog of input types; you don't invent controls, you compose them:

| Group | Types | Notes |
|---|---|---|
| Text | `text`, `textarea`, `inline_richtext`, `richtext`, `html`, `liquid` | `inline_richtext` = formatted text, no block tags |
| Numbers & toggles | `number`, `range`, `checkbox` | `range` needs `min`/`max`/`step`, optional `unit` |
| Choices | `select`, `radio`, `text_alignment` | `select` takes `options: [{value, label}]` |
| Color & type | `color`, `color_background`, `color_scheme`, `font_picker` | `color_scheme` plugs into the theme's scheme system — prefer it over raw colors in Dawn |
| Resources | `image_picker`, `video`, `video_url`, `url`, `product`, `product_list`, `collection`, `collection_list`, `page`, `blog`, `article`, `link_list`, `metaobject` | The pickers are why "ACF relationship field" needs no plugin here |
| Sidebar text | `header`, `paragraph` | Not settings — organization and hints in the editor panel |

Every setting takes `type`, `id`, `label`, and usually `default` and `info`. **`info` is not optional politeness** — it's the difference between a section a merchant uses and one they break.

**`blocks`** — repeatable, reorderable child units, each with its own `settings`. You render them yourself:

```liquid
{% for block in section.blocks %}
  {% case block.type %}
    {% when 'testimonial' %}
      <figure {{ block.shopify_attributes }}> … </figure>
  {% endcase %}
{% endfor %}
```

`{{ block.shopify_attributes }}` on each block's root element is **mandatory** — it's how the editor highlights and tracks blocks. Missing it is a review-protocol flag. `"max_blocks"` caps the count; a block type of `"@app"` lets merchants drop app blocks into your section.

**`presets`** — what makes a section appear in the editor's *Add section* picker, with sensible starter content:

```json
"presets": [{ "name": "Testimonials", "blocks": [{ "type": "testimonial" }, { "type": "testimonial" }, { "type": "testimonial" }] }]
```

No preset = a **static** section, only usable where a template JSON names it (that's `main-product`). With preset = merchant-addable anywhere — unless you fence it with `"enabled_on"` / `"disabled_on"` (e.g., keep testimonials out of the header group).

**Dynamic sources** — the feature ACF never had: on supporting setting types, the merchant can click the ⧉ icon and **connect the setting to a metafield** instead of typing a value. Same section, per-product content, zero code. You'll see the icon today and wire it for real in T1.5.

### Scoping — the professional tell

The same section can appear **multiple times on one page**, so nothing may leak. Shopify wraps every instance in `<div id="shopify-section-{{ section.id }}" class="shopify-section">`; Dawn's house pattern builds on it with a `{% style %}` block scoped by `section.id`:

```liquid
{%- style -%}
  .section-{{ section.id }}-padding {
    padding-top: {{ section.settings.padding_top | times: 0.75 | round: 0 }}px;
    padding-bottom: {{ section.settings.padding_bottom | times: 0.75 | round: 0 }}px;
  }
  @media screen and (min-width: 750px) {
    .section-{{ section.id }}-padding {
      padding-top: {{ section.settings.padding_top }}px;
      padding-bottom: {{ section.settings.padding_bottom }}px;
    }
  }
{%- endstyle -%}
```

(That mobile-gets-75% padding trick is pure Dawn — steal it.) Larger CSS goes in a per-section asset file loaded *inside* the section — `{{ 'section-testimonials.css' | asset_url | stylesheet_tag }}` — so it costs nothing on pages that don't use it. `{% stylesheet %}` / `{% javascript %}` tags exist too; Dawn's asset-file convention is our default.

One more rule that solves itself here: in a custom section, **every piece of storefront text is a setting** — heading, quotes, labels, all of it. That's how the no-hardcoded-strings rule is satisfied for custom work, with translation via schema `default`s left to the locale system when themes go multilingual.

## 2. Woo bridge

| You know (Woo) | Here (Shopify) | Where the mapping breaks |
|---|---|---|
| ACF field group + `get_field()` in a template | `{% schema %}` + `section.settings.x` | One file holds markup *and* field definitions — no plugin, no admin UI to configure, no database round-trip |
| ACF **repeater** | `blocks` | Reorderable in the editor by default; typed via `block.type` |
| ACF flexible content | Multiple block types in one section | Same `{% case %}` dispatch you'd write for layouts |
| Customizer API (`$wp_customize->add_setting/control` in PHP) | Declarative JSON | No registration code; the catalog of control types is fixed — you compose, never invent |
| Widgets & sidebars | Sections with presets | *Add section* anywhere a JSON template allows |
| Gutenberg block: `block.json` attributes + edit controls | Schema settings | Closest modern analogy — but rendered server-side in Liquid, zero React |
| ACF location rules ("show on product X") | Dynamic sources + alternate templates | The merchant connects data in the editor; you write no conditions |
| Field values in `wp_postmeta` / options | Per-instance values in the **template JSON** | Your settings live in the same files from T1.2 — merchant-shared state, versioned in Git |

**The mindset shift:** ACF fields were for *you* — you designed them, you consumed them in PHP. Schema settings are a **product you ship to a non-developer**. Labels, `info` lines, defaults, and grouping under `header`s *are the deliverable* — agencies judge the editor experience as much as the pixels. Schema design is API design.

## 3. Claude Code drill — the testimonials section

A classic agency deliverable: social-proof testimonials. Rich enough to touch six setting types, blocks, a preset, and scoping — with zero JavaScript (that's T2.2).

Branch: `git checkout -b t1-3-testimonials`.

### Part A — Design the schema by hand. No AI yet.

Schema design is the senior skill; you keep authorship of it. In `notes/testimonials-spec.md`, write the schema **as JSON, by hand**, from this functional spec:

**Section settings:** heading (`inline_richtext`, default "What customers say") · heading alignment (`text_alignment`) · color scheme (`color_scheme`) · desktop columns (`range` 2–4, step 1, default 3) · top/bottom padding (two `range`s, 0–100, step 4, unit px, default 36) — grouped under `header` entries ("Content", "Layout", "Spacing").

**Block type `testimonial`** (max 12): quote (`textarea`) · author (`text`) · role/company (`text`) · rating (`range` 1–5, step 1, default 5) · avatar (`image_picker`).

**Preset:** name "Testimonials", three starter blocks. **Fence it:** disabled in the `header` and `footer` groups.

Writing this JSON yourself once — ids, types, defaults, `info` lines — is what lets you *review* schema forever after. Ten minutes of squinting at the setting-type table above is the exercise.

### Part B — AI builds the section to your spec

Now hand Claude Code your schema and the standards:

> "Create `sections/testimonials.liquid`. Use exactly this schema: [paste your JSON]. Render: heading honoring the alignment setting; testimonial blocks as a responsive grid honoring the columns setting (single column under 750px); each block shows the quote, star rating rendered from the range value, author, role, and avatar. Avatar and role render only when set — use `!= blank`. Include `{{ block.shopify_attributes }}` on each block's root. Use Dawn's section-padding pattern with a scoped `{% style %}` block, and the color scheme via Dawn's `color-{{ section.settings.color_scheme }} gradient` class convention. Keep CSS small and inline in the style block for now. Theme Check clean, smallest complete implementation, explain anything that differs from how ACF-driven parts work."

Run the **full review protocol**. Two things to hunt for specifically: (1) does the star rating use a Liquid range loop — `{% for i in (1..block.settings.rating) %}` — or something needlessly clever? (2) did it invent any schema attribute not in your spec? Your hand-written JSON is the contract; diffs from it need a reason.

### Part C — The merchant test

You are now the least technical account manager at the agency. In the theme editor:

1. Add **Testimonials** to the homepage — confirm the preset lands with 3 starter blocks.
2. Configure everything: change alignment, scheme, columns. Add a 4th block, **reorder blocks by dragging**, delete one.
3. Try to break it: empty quote, no avatar, a 500-character author name, rating dragged to 1, a *second* copy of the section on the same page (scoping proof — different padding on each must not bleed).
4. Whatever broke or looked wrong: fix it in code, re-run the protocol. Merchant-proofing *is* the QA — this is the same pass you'll run before every S3 delivery.

### Part D — See the dynamic-source icon

Add the section to the **product** template in the editor. Click into the heading setting and find the connect-dynamic-source icon (⧉). Open the picker, see product metafields on offer, connect nothing yet — T1.5 gives you the data model behind that button. Remove the section from the product template after.

### Part E — Iterate like production

Ship a change request to yourself: *"Client wants to optionally hide the stars."* Prompt Claude Code to add a `show_rating` checkbox (default true) and gate the stars on it — smallest diff, schema and markup both. Review, then capture your configured homepage state the T1.2 way:

```bash
shopify theme pull --development --only "templates/index.json"
git diff   # your settings, written as data — commit deliberately
```

Commit the section, the spec note, and the template JSON.

## 4. Verification checklist

- [ ] Schema hand-written in `notes/testimonials-spec.md` before any AI involvement
- [ ] `sections/testimonials.liquid` matches your schema; deviations were justified and accepted consciously
- [ ] `{{ block.shopify_attributes }}` present on every block root; editor highlights blocks when clicked
