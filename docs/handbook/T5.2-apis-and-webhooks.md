# T5.2 — Admin API, Storefront API & Webhooks
**Module 5 · Tutorial 20 of 26 · Est. 5–6 hours**

**Goal:** Cross into the integration layer — the APIs that read and write the store from outside, and the webhooks that push events out. You'll build the classic client ask: **new order → your middleware → instant team notification**, then prove it the distributed-systems way: tamper test, replay test, failure test. Woo hooks were function calls; this is networking — the habits change accordingly.

**Prerequisites:** T4.3 (you've touched GraphiQL) and T1.5's "definitions are store data" insight, which today becomes "everything is API data."

## 1. Concept

### The API landscape — which door for which job

**Admin GraphQL API — the main door.** Everything in the store, readable and writable with scoped permissions: products, orders, customers, inventory, metafields, discounts, fulfillment. Four realities that shape professional use:

1. **Auth for client work = a custom app.** The single-store path: create a custom app in the store's admin, grant it the *minimum* scopes the job needs, install, and receive an Admin API access token. That token is a password to the business — env vars and secret managers only, never a repo, never a chat message. (Shopify's app-creation surfaces have been evolving toward the Dev Dashboard; whatever the store's admin shows, the shape is the same — app, scopes, token — and the toolkit settles the current clicks.)
2. **The API is versioned, quarterly** (`2026-01`, `2026-04`, …), each version supported about a year. Every integration pins a version in its URLs; every retirement is a maintenance event. Two consequences: date the version in your delivery notes, and notice the retainer logic — *"we keep your integrations current"* is recurring revenue hiding in an API policy.
3. **Rate limiting is cost-based, not request-based.** Each GraphQL query has a calculated cost drawn from a refilling points bucket; responses include your throttle status, and a `THROTTLED` error means back off and retry. Design queries lean; read the cost in the response extensions until it's instinct.
4. **Bulk operations** exist for big reads/writes — the real answer to "but I need all 40,000 products" that T1.5's fences pointed toward.

**Storefront API — the other door.** Tokenized, customer-context API for building buying surfaces: headless storefronts (Hydrogen), apps, kiosks. The decision rule that sorts every job in five seconds: **acting as the store/back office → Admin API; acting as a shopper or building a buying surface → Storefront API.** Headless is its own lane — for now, knowing which door a brief points at is the skill.

**Exploration tooling:** GraphiQL — the `app dev` console you used in T4.3, or Shopify's GraphiQL app installed on the store. Query interactively before any code exists; it's `theme console` for the data layer.

### Webhooks — events across a network

The store pushes JSON to your HTTPS endpoint on topics you subscribe to: `orders/create`, `orders/paid`, `products/update`, `customers/create`, `refunds/create`, `app/uninstalled`… Registration happens two ways — store-level in admin (Settings → Notifications → Webhooks, which shows the shared **signing secret**) or app-level (TOML subscriptions in a CLI app).

The delivery semantics are the professional meat — each one converts directly into a handler requirement:

| Reality | Your obligation |
|---|---|
| **Signed** — every delivery carries an HMAC-SHA256 header computed over the **raw body** with the secret | Verify it, timing-safe, before trusting a byte. And beware the classic bug: framework body-parsing consumes the raw body and breaks HMAC — capture raw bytes first |
| **At-least-once** — duplicates happen | Idempotency: dedupe on the delivery/event id |
| **Unordered** — `orders/updated` can beat `orders/create` | Handlers tolerate any arrival order |
| **Impatient** — slow acks count as failures | Return `200` fast; process async (queue pattern) |
| **Retried with backoff** over roughly two days, then the subscription itself is at risk | Monitor failures; a silently removed webhook is the worst outage — the quiet kind |
| **Notifications, not gospel** — deliveries can be missed | Critical flows get a **reconciliation sweep**: a periodic Admin API query for anything the webhooks didn't bring |

**Local development:** your machine isn't an HTTPS endpoint — tunnel it (cloudflared's free quick tunnels keep the series at $0; `app dev` auto-tunnels for app-registered webhooks). And the gift for iteration speed: **`shopify webhook trigger`** sends realistic sample payloads on demand — test deliveries without placing orders.

### Middleware — and the honesty ladder above it

Middleware is the small service you own between Shopify and a destination: it holds secrets, verifies signatures, absorbs retries, transforms payloads, and fans out (Discord, Slack, email, a sheet, an ERP). A tiny Node service on any cheap host — or serverless — carries most agency integrations.

But senior scoping climbs a ladder before writing code: **Shopify Flow** (free, native automation — including an HTTP-request action) handles many simple notification and tagging flows with zero code · **Zapier/Make** cover the next band · **middleware** earns its keep when transformation, business logic, multiple destinations, or reliability requirements exceed the no-code tier. Quoting middleware for a Flow-sized problem is billing for ego; the drill builds middleware because the *skill* must exist for the jobs above the ladder.

## 2. Woo bridge

| You know (Woo) | Here (Shopify) | Where the mapping breaks |
|---|---|---|
| WP REST + application passwords | Admin GraphQL + scoped custom-app token | Scopes are granular; the token is per-app, revocable, auditable |
| `register_rest_route` custom endpoints | Middleware routes — on *your* server | The extension point moved off their infrastructure entirely |
| `add_action('woocommerce_new_order')` — in-process, guaranteed, ordered, same request | `orders/create` webhook — cross-network, at-least-once, unordered, retried | The deepest break: from function calls to distributed systems |
| Woo webhooks (you may have shipped these — same HMAC idea) | Same idea, industrialized semantics | Your HMAC instinct transfers; the retry/removal/reconciliation discipline is new |
| WP-Cron polling loops | Webhooks + reconciliation sweep | Push first, sweep for truth |
| Direct `$wpdb` integrations | API-only, versioned, cost-limited | No back door exists; version pinning is the new update-safety |
| Keys in `wp-config.php` | Env vars / secret managers | Same principle, sharper stakes |
| Zapier-for-Woo reflex | The ladder: Flow → Zapier/Make → middleware | Flow's existence changes what deserves code at all |

## 3. Claude Code drill — order ping, the distributed-systems way

The build: `orders/create` → local Node middleware (tunneled) → **Discord**: *"🎉 New order #1001 — $45.99 · 2 items"*. Discord because a webhook URL there takes thirty seconds and zero auth (Slack is the same shape with more ceremony). New repo: `order-ping-middleware/`, plus notes in the theme repo.

### Part A — API literacy first (~45 min)

1. Create the custom app in your dev store's admin; grant **read_orders, read_products** only. Token straight into `.env`; `.gitignore` before the first commit; add the secrets rule to this repo's fresh `CLAUDE.md` (*secrets from env only; flag any credential appearing in code or output*).
2. GraphiQL reps — Claude Code drafts, **you run and verify against the admin**: five products with prices · the last three orders with line items and totals. Find `throttleStatus` in the response extensions; read your query's cost out loud. Note the API version in the URL you're hitting; write it in the notes — it just became a maintenance date.

### Part B — The middleware, spec-first (~60 min)

Hand-write the spec before the prompt — it's six lines and it *is* the review standard:

1. `POST /webhooks/orders-create`: capture **raw body** → verify HMAC (timing-safe, secret from env) → on failure `401`, log, stop → on success **`200` immediately** → process async → dedupe on the delivery id (in-memory set for the drill; note that production means a store) → format order number, total, item count → POST to the Discord webhook URL (env).
2. `GET /health` → `200`.

Master prompt: the spec + *"smallest complete Node service; raw-body capture before any JSON parsing on the webhook route; no framework magic that hides the raw body; list anything you couldn't satisfy."* Review hunts, in order of blood spilled historically: **HMAC computed over the raw bytes** (the parsed-body bug is the #1 webhook failure in the wild) · timing-safe comparison · ack-before-work ordering actually async · both secrets from env · dedupe present.

### Part C — Wire it and feel the magic (~30 min)

1. Run the service; open a cloudflared quick tunnel; note the public URL.
2. Admin → Settings → Notifications → **Webhooks** → create `orders/create` → your tunnel URL. Copy the **signing secret** shown there into `.env`.
3. Create a Discord server + channel webhook; URL into `.env`.
4. **Place a test order.** Watch the 🎉 land. That round trip — store event → your code → team channel — is the S4 integration service in miniature, and it never stops feeling good.

### Part D — The distributed-systems proofs (~60 min, the actual lesson)

1. **Iteration without orders:** `shopify webhook trigger` for `orders/create` at your endpoint — sample payloads on demand. Use it for everything below.
2. **Replay proof:** deliver the same payload twice → **one** Discord message. Idempotency, witnessed.
3. **Tamper proof:** hand-craft a `curl` with a wrong signature → `401`, nothing posted, attempt logged. Security, witnessed.
4. **Failure proof:** make the handler return `500`, trigger, watch redelivery arrive on the retry schedule (logs + patience) → fix → confirm recovery. Retries, witnessed — and now you know what a failing endpoint *feels* like from the receiving side.
5. **The miss:** kill the tunnel, place a real test order, restore — the order exists, no ping ever came. Write the reconciliation design in the notes (an hourly Admin API sweep for orders newer than the last seen, using Part A's query — design only, ~a paragraph). Webhooks notify; the API is truth.

### Part E — Map and package (~25 min)

1. `notes/integration-map.md` — the master "where does logic live" table, now nearly complete across the series: storefront behavior → theme · checkout UI → extensions · pricing/eligibility → Functions · analytics → pixels · store data in/out → **Admin API** · buying surfaces → Storefront API · events out → **webhooks + reconciliation** · automation ladder → Flow → no-code → middleware.
2. Delivery notes (Template 3, integration edition): what runs where, which secrets exist and live where, the pinned API version and its date, the retry/monitoring note, and the evidence (screenshots of the four proofs — T5.1's evidence-trail standard now covers integrations too).
3. Productization line: *order-notification middleware — extraction candidate; also evaluate against Flow before ever quoting it again.*
