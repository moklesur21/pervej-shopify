# T4.2 — Build a Checkout UI Extension
**Module 4 · Tutorial 17 of 26 · Est. 4–6 hours**

**Goal:** Ship your first two checkout UI extensions — a merchant-placeable **trust-badges block** and a **delivery-note field** whose value lands on the real order. Along the way you cross the biggest tooling boundary in this series: you're leaving theme-land and entering **app-land**, with a new CLI workflow, a new repo shape, and a release pipeline.

**Prerequisites:** T4.1's map. This is rep #1 of the house rule — checkout work stays off client stores until these reps are done.

---

## 1. Concept

### The context shift: extensions live inside apps

A checkout UI extension cannot exist on its own — it ships inside an **app**. For client work, that means an **extension-only custom app**: no embedded admin UI, no App Store listing — just a vehicle that carries your extensions onto one store. Your workflow grows four new verbs:

```bash
shopify app init          # scaffold the app (choose the extension-only flavor when prompted)
shopify app generate extension   # add an extension to it
shopify app dev           # run the dev server; live-preview on your dev store
shopify app deploy        # create a released app version
```

Three structural changes from theme work, worth internalizing before touching code:

1. **A release pipeline exists now.** Themes were "push files." Apps have **versions**: `deploy` snapshots your extensions into a version and releases it. Rollback is picking a previous version. Your Git discipline gains a sibling.
2. **App management lives in the Dev Dashboard** (the newer home for app config, migrating from the old Partner Dashboard). `app dev` and `app deploy` handle most of it from the terminal; know where the dashboard is when you need scopes, versions, or install links.
3. **Ownership is a white-label question.** A custom app belongs to a partner organization. On agency work, decide early whose org carries it — building in the agency's org (or transferring) keeps their brand on everything, per house discipline. One sentence in scoping saves an awkward migration later.

Development stores support building and previewing checkout extensions — plan gating bites at **client install time**, which is exactly why T4.1's per-client checkpoint exists.

### Anatomy of an extension

```
my-app/
└── extensions/
    └── trust-badges/
        ├── shopify.extension.toml   ← the contract: targets, capabilities, settings
        └── src/                     ← the component code
```

**The TOML is the schema of this world.** It declares:

- **Target(s)** — where the extension can render. Two families, straight from T4.1: *block targets* like `purchase.checkout.block.render` (the merchant positions the block in the checkout editor) and *static targets* pinned to core features (before/after delivery address, shipping methods, order summary…).
- **Capabilities** — opt-in permissions (network access, api access) that trigger scrutiny; request nothing you don't use.
- **Settings** — merchant-editable fields, **edited in the checkout editor**. Read that twice: this is your T1.3 section schema instinct, transplanted. Same discipline applies — labels, sensible defaults, nothing hardcoded that a merchant might want to change.

**The code side, current era:** extensions render **Polaris web components** (`s-` prefixed elements — banners, text, fields, stacks) and talk to checkout through a global `shopify` API object exposing reactive values (cart lines, cost, buyer identity where permitted) and write methods (attribute and note changes). **The trap to brief your AI on:** everything ≤ API 2025-07 was React-based (`useApi`, `useApplyAttributeChange`, `@shopify/ui-extensions-react`) — the internet and model memory are saturated with that flavor, and it's legacy. Your defense is structural: **the scaffold is the source of syntax truth.** Generate first, read what current Shopify scaffolding produces, and make the AI extend *that* idiom — with the toolkit resolving disputes.

**Data flow for the field build:** an input writes to a **cart attribute** (or the order note) via the API's change methods; attributes survive checkout and appear on the **order in admin** — readable by staff, by apps, and by notification templates (surfacing them in emails is a template edit — quote it as its own line item). What you cannot write: arbitrary order fields. The socket is attributes/note; the socket is enough.

The sandbox contract from T4.1 governs everything here — no DOM, no CSS overrides, Shopify components only, merchant branding always wins. Design *within* it and your extension survives every checkout update Shopify ever ships.

## 2. Woo bridge

| You know (Woo) | Here (Shopify) | Where the mapping breaks |
|---|---|---|
| Checkout field: `woocommerce_checkout_fields` + save to order meta + admin display code | Extension field → attribute change → **on the order automatically** | The save/display plumbing you hand-wrote is platform behavior now |
| Trust badges: template hook injection at a priority you chose | Block target + **merchant places it** in the checkout editor | Position is the merchant's power, not your hook priority |
| Shipped as a snippet in `functions.php` / plugin | Shipped as a **versioned app artifact** | Deploys, versions, rollback — code has a release pipeline |
| Field config via ACF or hardcoded arrays | TOML settings, edited in the checkout editor | Your section-schema muscle, verbatim |
| Show field value in emails via `woocommerce_email_order_meta` | Attribute available to notification templates | Still a template edit — still its own scope line |
| Test on staging | `app dev` live preview on the dev store | Faster loop, same discipline |

## 3. Claude Code drill — one app, two extensions

Branch-less for once: this is a **new repo**. Create `checkout-extensions-lab/`.

### Part A — Scaffold and orient (~40 min)

1. `shopify app init` → choose the **extension-only** flavor → connect it to your Partner org and dev store when prompted.
2. `shopify app generate extension` → **Checkout UI** → name it `trust-badges`.
3. Tour before touching: read `shopify.extension.toml` top to bottom, then the scaffolded `src/` — this is today's idiom, whatever it is. Have Claude Code annotate the scaffold file-by-file, and verify one claim against the toolkit.
4. Write this repo's `CLAUDE.md` — the theme one won't do. New hard rules: *current-API idioms only — the scaffold and toolkit are truth, React-era extension patterns (`useApi`, `@shopify/ui-extensions-react`) are legacy and must be flagged, not used* · *request no capabilities we don't use* · *all merchant-facing text comes from TOML settings* · *sandbox contract respected — list it*.
5. `shopify app dev` → open the checkout preview it prints. Empty extension rendering in a real checkout: the loop is alive.

### Part B — Trust badges (~60 min)

**Spec by hand first** (T1.3 muscle, new syntax): three TOML settings — badge texts with defaults like "Free returns", "Secure checkout", "Ships in 24h" — plus a sketch of the render: a horizontal stack of icon-plus-text items, blank-guarded so an emptied setting drops its badge.

Then the master-prompt pattern, extension edition: your spec + *"extend the scaffolded idiom exactly — same component style, same API access pattern; Shopify components only; list anything the sandbox prevented."* Review protocol with two extension-specific hunts: **any React-era import or hook is an automatic reject**, and **no capability added** to the TOML that the spec didn't require.

### Part C — Place it like a merchant (~15 min)

Checkout editor → add your block → drag it between positions (above the pay button, in the order summary) → edit the badge texts **in the editor**. That's your TOML settings rendering as merchant UI — the T1.3 payoff, relocated to the money page. Screenshot it placed; that's proof-kit material.

### Part D — The delivery-note field (~60 min)

`shopify app generate extension` again → `delivery-note`. Spec by hand: one optional multiline field, label and placeholder from TOML settings, a max-length cap, value written as a **cart attribute** (`Delivery note`). Build to the scaffold idiom, review, then run the proof that matters:

**Place a full test order with a note typed in — then open the order in admin and find your attribute on it.** That round trip (checkout input → platform → order record) is the entire value proposition of this extension class, witnessed. Bonus proof: the attribute is also visible to the thank-you page context and to staff fulfilling the order.

### Part E — Deploy and package (~30 min)

1. `shopify app deploy` → read what it tells you: a **version** was created and released. Run it again after a trivial change — version two. Feel the pipeline.
2. Write `delivery-notes.md` (Template 3, checkout edition): what was built · where the merchant edits each thing (checkout editor, both blocks) · **what a client install involves** — custom app install on their store, plan check per T4.1, block placement, and the email-template line item if they want the note in notifications · assumptions.
3. Commit everything.

### Part F — The traps, sprung on purpose (~15 min)

1. Ask Claude Code, cold: *"How do I read cart lines in a checkout UI extension?"* If the answer reaches for React hooks, you've watched the trap fire — correct it with the CLAUDE.md rule and the toolkit, and note how convincing the stale answer looked.
2. Try to add a `<div>` with custom CSS to the badges. Watch the sandbox refuse. The wall, touched personally, is a wall you can describe to clients with total confidence.
