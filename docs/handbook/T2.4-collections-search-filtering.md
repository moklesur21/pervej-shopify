## 1. Concept

### A. Collection pages, pagination, sorting

The collection template's main section loops `collection.products` — inside a mandatory tag:

```liquid
{% paginate collection.products by 24 %}
  {% for product in collection.products %} … {% endfor %}
  {% render 'pagination', paginate: paginate %}
{% endpaginate %}
```

`{% paginate %}` is not optional decoration: loops over collection products cap at 50 without it, and there is no `posts_per_page => -1` on this platform. The `paginate` object gives you pages, current page, and part links.

Sorting is URL state: `?sort_by=price-ascending`. In Liquid, `collection.sort_by` is the active sort and `collection.sort_options` lists what the platform offers (best-selling, alphabetical, price, date). You render the control; the platform does the sorting.

### B. Storefront filtering — config, not code

The part that reorganizes your Woo instincts: **which filters exist is merchant configuration, not theme code.** Filters are set up in the free, Shopify-made **Search & Discovery app** — availability, price, product options (color, size…), vendor, product type, and **metafields** (T1.5 cashes another check). The theme's job is to *render* what's configured:

```liquid
{% for filter in collection.filters %}
  {% case filter.type %}
    {% when 'list' %}        {% # values with label, count, active state %}
    {% when 'price_range' %} {% # min/max inputs against filter.range_max %}
    {% when 'boolean' %}     {% # e.g. availability %}
  {% endcase %}
{% endfor %}
```

Applied filters live in the URL (`filter.v.…` / `filter.p.…` params). The rendering contract: filter UI sits in a **GET form**; submitting reloads the collection filtered. Dawn upgrades that baseline with `facets.js` — a `FacetFiltersForm` custom element that intercepts changes, fetches the **section-rendered** collection grid for the new URL, swaps the HTML, and `history.pushState`s the address bar. Look at what that is: **T2.3's exact architecture** — URL as state, Liquid as the single renderer, JS as courier. Once you see the pattern, half this platform is the same building.

Three professional consequences:

1. **"Add a brand filter" is config work** (S&D app), not a build — quote accordingly, deliver in minutes, look like a wizard.
2. **A filter that "doesn't show up" is usually data**, not code: the filter only renders where products actually carry the values.
3. **No-JS fallback comes free** if you keep the GET form honest — the form submits, the page reloads filtered. Progressive enhancement without trying.

### C. Search

- Standard search: `/search?q=…` → the search template, `search.results` (products, articles, pages), `search.terms`, `search.results_count` — and `search.filters`, same system as collections.
- **Predictive search:** `GET /search/suggest` powers the type-ahead. Dawn's `predictive-search` component fetches suggestions rendered through the Section Rendering API and swaps in HTML — courier pattern, third appearance.
- Honesty for scoping: native search is *good*, not Algolia. Synonyms/boosts live in Search & Discovery; genuinely advanced relevance needs an app — that's an evaluation conversation (T5.3), not a default.

### D. The `WP_Query` replacement map — Module 1's promise, closed

"I need products by X" → the tool:

| Need | Tool |
|---|---|
| Products of the current collection page | `collection.products` + `paginate` |
| Products matching attributes/price/stock, user-chosen | **Filters** (S&D config + `collection.filters`) |
| A fixed known set, merchant-curated | `collection` / `product_list` **section settings** (T1.3) or an automated collection's rules (T0.2) |
| One known product / a few by handle | `all_products['handle']` (20/page) · `collections['handle'].products` (50 cap) |
| Related / complementary to a product | Recommendations endpoint (T2.3) |
| Text search, typed by the user | `/search` + predictive |
| Structured custom data | Metafields/metaobjects (T1.5) |
| Anything beyond all of this | **The APIs** (T5.2) — or the honest "not on this platform" |

Copy this table into `notes/query-map.md`. It's the answer to a whole genre of client requests.

## 2. Woo bridge

| You know (Woo) | Here (Shopify) | Where the mapping breaks |
|---|---|---|
| `WP_Query` + `tax_query` + `meta_query` | The map above | Queries you *composed* become state you *render*: the URL is the query, the app is the config, the platform is the engine |
| `pre_get_posts` surgery | Doesn't exist | You cannot rewrite the main query — you offer sort options and filters |
| FacetWP / layered-nav plugin stack (licenses, index rebuilds) | **Native** filtering via S&D + `collection.filters` | No plugin, no indexing server, no license renewal — a Woo cost center that's just… gone |
| Faceted AJAX (fragment refreshes) | `facets.js` + Section Rendering | Same UX, platform-blessed transport |
| `?orderby=price` | `?sort_by=price-ascending` | Fixed option set, platform-sorted |
| Relevanssi / SearchWP | Native search + predictive + S&D tuning | Apps only for genuinely advanced relevance — scoping call, not reflex |
| `posts_per_page => -1` | `{% paginate %}` or nothing | The 50-cap is a fence, not a suggestion |

## 3. Claude Code drill — a quick-filter bar inside the machine

Client-shaped brief: *"Filters feel buried — we want a quick-filter row above the grid: color swatches and an in-stock toggle, like [big brand site]."* Branch: `t2-4-quick-filters`.

### Part A — Make the store filterable (~30 min, admin)

1. Give your dev-store products real discovery data: product types, vendors, a **Color option** on several products, sensible tags. (Test data helps; top up by hand.)
2. Install **Search & Discovery** (free, by Shopify) and configure filters: Availability, Price, Color, Vendor — **plus one metafield filter**: define `custom.material` (single line text) on products, fill it on a few, add it as a filter in S&D.
3. Load your collection page — watch the filter panel populate from config alone. Zero theme code so far.

### Part B — Trace the facets machine (~45 min)

Network tab open: apply a filter in Dawn's UI. Find the fetch — a collection URL carrying `filter.…` params and a section id — and the HTML that returns. Then walk `main-collection-product-grid.liquid` → `facets.liquid` → `facets.js` with Claude Code annotating, you verifying: where `collection.filters` is looped, where the GET form lives (note its `id`), where pushState happens. Output: `notes/filtering-flow.md`. Finish with the URL-as-state proof: hand-edit the address bar (`?filter.v.availability=1&sort_by=price-ascending`), hit enter, watch the server oblige.

### Part C — Build the quick-filter bar

**The architectural rule of the build: your bar's inputs must live *inside the theme's existing facet form*,** so Dawn's own listeners, fetch, and pushState machinery drive them — enhance, never rebuild, third tutorial running. Practically: a new snippet rendered within `facets.liquid`'s form region, above the standard UI.

Spec by hand, then build with the master prompt:

- **Color swatches:** find the Color filter in `collection.filters`, render its values as swatch-styled checkboxes — `name`/`value` from the filter value's own params, `checked` from its active state, label showing the count, swatch color derived from the value name with a small Liquid map for the odd ones. **Instruct the AI to mirror how the theme's own facet inputs are named and to verify filter-value properties with the toolkit rather than assume** — this object's property names are exactly where memory gets fuzzy.
- **In-stock toggle:** the availability boolean filter as a single styled switch, same rules.
- **Results line:** "{{ collection.products_count }} products" that updates with the swaps.
- Render the bar only when the relevant filters exist and carry values (consequence #2 above, guarded).
- *Stretch:* active-filter chips with per-value removal links + clear-all, using the removal URLs the filter objects expose.

Review protocol hunts: inputs genuinely inside the form (inspect the DOM) · no second fetch layer invented beside `facets.js` · counts and active states from the platform, not hardcoded.

### Part D — The proofs

1. **Courier proof:** toggle a swatch — Network tab shows the theme's own section fetch; grid, bar, counts, and URL all update.
2. **No-JS proof:** JS disabled → the bar still filters via honest GET submit.
3. **State proofs:** filtered URL pasted in a new tab reproduces the view; back button walks filter history; sort + filter + pagination coexist.
4. **Config proof:** your `material` metafield filter appears in the standard panel untouched by any of today's code — say out loud why.
5. Console clean · 360/390/768 on the bar · Theme Check clean.

### Part E — Search, eyes only (~15 min)

Type in Dawn's search with the Network tab open; find the predictive fetch and the rendered HTML in its response; skim `predictive-search` in the assets. Add three lines to `notes/filtering-flow.md`: same courier, different endpoint. No build — recognizing the pattern *is* today's search deliverable.
