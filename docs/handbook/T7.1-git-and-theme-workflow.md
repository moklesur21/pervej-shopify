# T7.1 — Git & Theme Workflow Discipline
**Module 7 · Tutorial 24 of 26 · Est. 4–5 hours**

**Goal:** Run one client change request end to end — brief → scope → branch → build → preview → deploy → rollback — the way it will happen on a real agency store, and come out with a written **deploy runbook** for both the GitHub-connected and CLI-only paths. Everything before this tutorial answered "can you build it?" Module 7 answers the only question an agency actually cares about: **"can you be trusted with the live store?"**

**Prerequisites:** Any theme build from Module 2 to reuse as the change request's feature; T1.2 (you know what lives in `templates/*.json`, `sections/*.json` and `config/settings_data.json`); a GitHub account with a private repo you own. Strategy doc **Section 8** (Delivery System) open beside you — this tutorial is 8.1 and 8.2 made physical.

## 1. Concept

### 1.1 Why this module exists

The two-regression rule: two defects reaching an agency in scoped work and we're quietly dropped. Almost every regression that reaches a Shopify client is not a bug in the feature — it's a **workflow** failure: pushed stale settings over the merchant's homepage, edited the live theme "just for a second," deployed without a backup, lost a merchant's editor changes in a merge. This tutorial makes those failures structurally impossible, not just unlikely.

### 1.2 Shopify's theme state model

There is no server. A theme is a **record in Shopify**, not files on disk. Everything about workflow follows from that.

| Thing | What it is | Workflow meaning |
|---|---|---|
| **Live (published) theme** | The one record customers see | Never edited directly. Ever. Not "for a quick fix," not "just a setting." |
| **Theme library** | Unpublished themes on the store; **capped** (20 on standard plans) | Your staging, previews and backups all live here — and compete for slots. Clean up or you'll be unable to create a backup when you most need one. |
| **Development theme** | A temporary theme the CLI creates per developer per store for `shopify theme dev` | Yours alone; disposable; never share its preview as "staging." |
| **Preview link** | A shareable URL for any unpublished theme | This *is* the client review surface (8.1 step 6). |
| **Publish** | Swapping which record is live — atomic, instant | Deploy **and** rollback are the same operation. That's better than Woo — if you kept the backup. |

**Two kinds of change, only one of them stageable.** Theme code stages perfectly as an unpublished theme on the same store. Store configuration does not: products, collections, discounts, shipping, checkout settings, app installs and app configuration are **live the moment you save them**. For data- or app-touching work, "staging" means either a separate staging store the agency owns, or a written runbook with export-before-change and a rollback path. Say which one in the scope. Scope creep from "just a theme change" into "and also configure the app" is where staging silently stops existing.

### 1.3 The code/data blend — the #1 way freelancers break live stores

In Woo, code is files and content is the database; Git tracks code and can't hurt content. On Shopify, the theme's JSON files (`config/settings_data.json`, `templates/*.json`, `sections/*.json` groups) are **merchant data** — every theme-editor save writes into them — and they sit in the same folder as your Liquid.

So `shopify theme push` is a **data operation**. Push a two-day-old local copy of `templates/index.json` over a theme the merchant re-arranged yesterday and their homepage reverts, silently, with no error. Rules, in order of importance:

1. **Never push to a live theme.** The CLI refuses without `--allow-live`; that flag is banned in our `CLAUDE.md`.
2. **Pull JSON before you push code.** `shopify theme pull --theme <id> --only "templates/*.json" --only "sections/*.json" --only "config/settings_data.json"` refreshes the data files from the target theme before any push to it.
3. **`.shopifyignore`** keeps settings files out of routine code pushes; **`--nodelete`** prevents the push from deleting remote files you don't have locally (app-generated files, merchant-uploaded assets); **`--only`** makes surgical pushes possible; **`--strict`** refuses to push if Theme Check has errors — our default.
4. In a merge conflict on a JSON file, **the merchant's version wins** unless your scope explicitly changed that setting.

### 1.4 The duplicate-the-live-theme rule

Before any deploy: **Actions › Duplicate** on the live theme, renamed to a convention (`2026-09-10 · live backup · pre-{task}`). The duplicate is a snapshot *including the live JSON state* — the only true backup of the merchant's current settings. Rollback is "publish the backup" — seconds, no Git involved. Because of the library cap, part of the deploy runbook is **deleting the oldest backup** once the warranty window on its task has closed (keep the last two).

### 1.5 The GitHub integration — what it actually does

Install the Shopify GitHub app, then **Online Store › Themes › Add theme › Connect from GitHub**: pick repo + branch. From then on:

- **Two-way sync.** Commits to the branch update the theme; **every save in the theme editor, code editor, or a theme app is committed back to the branch by the `shopify` bot, naming the shop and the last editor.** This cannot be disabled. Consequence: your feature branch and `main` receive commits you didn't make. `git pull` before every session, no exceptions.
- **One branch ↔ one theme.** A branch connected as an unpublished theme is a live-data preview: the natural staging theme. Publish it and it *stays* connected — `main` connected and published means the live theme is Git-tracked. Disconnect a branch and you **can't reconnect** it — reconnecting creates a new theme, and the library cap ticks up.
- **Buildless only.** The branch must match the standard theme folder structure; anything else is ignored. Dawn and Horizon are buildless, so this is fine. A build pipeline means a compiled `deploy` branch (Shopify's recommended pattern) — a project decision, not a change-request decision.
- **Conflicts are crude.** The code editor overwrites the GitHub version with no warning; the theme editor warns on save. If the theme looks out of sync: **Actions › Reset to last commit**; **View logs** beside "Last saved" shows the sync events.
- **Permissions are GitHub's.** Only org members with write access can connect branches; outside collaborators can't; a personal repo where you're merely a collaborator won't even appear. For agency work: **the repo lives in the agency's GitHub org** (or ours, transferred on final payment — IP clause), the app is granted access to *that repo only*.

When the agency won't install the app on a client store (it happens — some won't grant a third-party GitHub app admin access), the **CLI-only path** does the same job with `--unpublished` themes and discipline. Drill F builds it. Both paths ship the same runbook.

### 1.6 Access and identity

- **Collaborator account** via the Partner Dashboard, using the store's collaborator request code, with scoped permissions (Themes; only what the task needs). This is the normal white-label access — the agency grants it, revokes it, and sees your name in the bot's commits.
- **Theme Access app**: a store-scoped password for CLI use (`--password` / `SHOPIFY_CLI_THEME_TOKEN`) without any admin login — right for CI or a subcontractor who should never see the admin.
- **Never a shared owner password.** House rule 8.2, and the one an agency will remember you for keeping.

### 1.7 The house flow, on Shopify

Strategy doc 8.1, with the platform filled in:

1. **Brief in** → 2. **Written fixed scope** (deliverables, exclusions, "theme code only" or the data/app plan) → 3. **Approval + invoice** → 4. **Backup**: duplicate live → 5. **Branch** `feat/{task}` off a freshly pulled `main` → 6. **Build** locally with `shopify theme dev` against the client store's dev theme; Claude Code + line-by-line review → 7. **Theme Check clean**, `--strict` → 8. **Preview theme** (connected branch, or `push --unpublished`) → 9. **QA** (T7.2's checklist) → 10. **Staging review**: preview link + Loom, 5-business-day window → 11. **Deploy**: pull merchant JSON, merge to `main` (or push to the connected/duplicated theme and publish) in the agreed window → 12. **Verify live** (purchase flow, console, Lighthouse) → 13. **Handoff + 14-day warranty** → 14. Retire the oldest backup when its warranty closes.

**The diff is the deliverable.** Before any push, `git diff --stat main..feat/{task}`: every file outside the written scope is a red flag — and AI-assisted builds produce exactly this failure (a "helpful" reformat of an unrelated section, a fixed typo in a locale file nobody asked about). Out-of-scope files get reverted, not shipped.

### 1.8 Woo bridge

| Woo | Shopify | Where it breaks |
|---|---|---|
| Staging = a server with a DB copy (host staging, Local) | Staging = an **unpublished theme on the same store** | Only theme code stages. Products, discounts, shipping, apps, checkout settings are live on save — they need a staging store or a runbook |
| Code in files, content in the DB; Git can't touch content | Theme JSON files carry merchant content and settings, in the same folder as code | Every push is a data operation; stale JSON overwrites the merchant's work with no error |
| Deploy = files to server (SFTP, `git pull`, CI) | Deploy = **publish** a theme (or the connected `main` syncing) | Atomic, instant, and the same mechanism as rollback — an upgrade, if you kept the backup |
| Backup = files + DB dump | Backup = **duplicate the live theme** | Backs up the theme only, not store data |
| Child theme inherits parent updates | The theme is a fork; Dawn/Horizon updates don't flow in | A theme version update is a project, never a change request |
| Plugin-conflict check before handoff | App block / app embed check + Theme Check | Apps render through blocks and embeds; a section change can silently drop an app block |
| WP-CLI over SSH; "fix it on the server" | Shopify CLI over the API; no server | Nothing happens outside the API, and nothing happens on the live theme |
| Shared SFTP / wp-admin credentials (bad, but common) | Collaborator accounts with scoped permissions; Theme Access passwords for CLI | Never an owner login — and the agency can see exactly who changed what |
| Feature branches; only you commit | Feature branches **plus the `shopify` bot** committing merchant edits to connected branches | Your branch changes without you; pull before every session, merge with the merchant's data winning |

## 2. Claude Code drill — one client change request, end to end

**The scenario.** Your dev store is "the client's live store." Its published theme is "the live theme" — from this drill on, you treat it with production paranoia. The brief arrives from the agency:

> *"Client wants a 'Pairs well with' block on the product page showing 3 hand-picked products (merchant chooses them per product), and the announcement bar should rotate three messages instead of one. Nothing else should change. They'd like it by Thursday."*

### Setup (Drill 0)

1. Private GitHub repo `{client}-theme` (empty). Install the Shopify GitHub app for your GitHub account; grant it access to **this repo only**.
2. Locally: `shopify theme pull --live` into the repo folder → this is the baseline. Commit as `chore: baseline — live theme as of 2026-09-10`. Push to `main`.
3. Add `.shopifyignore` (settings files; anything non-theme like `docs/`, `.github/`) and a `shopify.theme.toml` with two environments: `dev` (your dev theme) and `live` (store only — **no theme ID**, so nothing can push there by accident).
4. Add a house-rules block to `CLAUDE.md`: never `--allow-live`, never `--publish` from the CLI on a client store, always `--strict` and `--nodelete`, pull JSON before pushing to any shared theme, scope diff before every push.
5. Write `docs/scope-{task}.md`: deliverables (2), exclusions ("no changes to any other section, template, locale or settings"), the data question answered ("theme code only — the merchant picks the paired products via a product-list metafield; defining the metafield is a live admin change, listed as such"), the deploy window, the 5-day review window.

### Drill A — Backup and branch

1. Admin: duplicate the live theme → rename `2026-09-10 · live backup · pre-pairs-well-with`. Count the library. Note the number in `docs/deploy-runbook.md` (you'll build this file through the drill).
2. Connect **`main`** from GitHub as an unpublished theme, then **publish** it: the live theme is now Git-tracked. Test the sync: change the announcement text in the theme editor → open the branch on GitHub → find the `shopify` bot's commit naming the shop and you → `git pull`. You just watched the bot edit your repo. That's normal life now.
3. `git checkout -b feat/pairs-well-with` and connect **that branch** as a second unpublished theme. Its preview link is your staging URL.

### Drill B — Build, with the diff as the deliverable

1. Hand-write the section/metafield spec first (T2.1 discipline): a `product.metafields.custom.pairs_well_with` product-list metafield rendered by a product-page block; the announcement bar gains a blocks-based rotation.
2. Claude Code builds against the spec; `shopify theme dev` on your dev theme for the loop. Line-by-line review as always.
3. **Scope diff before anything leaves your machine:** `git diff --stat main..feat/pairs-well-with`. Only the files in scope may appear. If Claude "tidied" anything else — revert those hunks. Record what you reverted in the runbook: that list becomes your personal AI-side-effect watchlist.
4. Theme Check clean. Commit in small, scoped commits. `git push` → the connected feature theme updates itself. Open its preview link on your phone: that's what the agency will see.

### Drill C — The merchant edits live mid-project *(the trap)*

While your branch is open, play the merchant: in the theme editor **on the live theme**, reorder two homepage sections and change a collection-list heading. Save.

1. Observe the bot's commit land on `main`.
2. `git checkout main && git pull`. `git checkout feat/pairs-well-with && git rebase main` (or merge — pick one and put it in the runbook). If `templates/index.json` conflicts, resolve it with **the merchant's version** — your scope never touched the homepage.
3. Push the feature branch; reload the preview; confirm the merchant's homepage change is there *and* your feature works. This is the exact sequence that loses merchant work when done carelessly; you've now done it carefully once.

### Drill D — Staging review

Share the feature theme's preview link plus a two-minute Loom (T7.2 will formalize the recording; keep it simple here). Write the review message you'd send an agency PM: what to check, the 5-business-day window, what "approved" means. Put it in `docs/` as a template.

### Drill E — Deploy, verify, roll back, fix forward

1. **Pre-deploy JSON pull** (belt and braces even with the integration): `shopify theme pull --live --only "templates/*.json" --only "sections/*.json" --only "config/settings_data.json"` onto `main`; commit if anything changed.
2. **Deploy** = merge `feat/pairs-well-with` into `main` and push. The live theme updates in place. Verify live: the feature, the merchant's homepage change, full purchase flow, console clean, Lighthouse three-run median vs. the pre-change number.
3. **Simulate a post-deploy regression** — the agency reports the rotating bar breaks on Safari. **Roll back**: publish the backup duplicate. Time it. Then notice the subtlety: the live theme is now the *unconnected* duplicate, and `main` still contains the feature. Rollback on Shopify is a theme swap, not a Git operation.
4. **Fix forward**: fix on the branch, re-test, merge to `main`, **re-publish the connected `main` theme**. The store is back on Git.
5. Delete the feature theme from the library (keep the branch). Note when the backup can be retired (warranty close + a day).

### Drill F — The CLI-only path

Some agencies won't install the GitHub app on the client store. Repeat the essentials without it:

1. `shopify theme push --unpublished --theme "feat-pairs-well-with" --strict --nodelete` → creates the staging theme; `shopify theme list` to find IDs; the preview link comes back with `--json`.
2. Iterate with `shopify theme push --theme <id> --strict --nodelete` (`--only` for surgical pushes).
3. Deploy without the integration: duplicate live → **push to the duplicate** (`--theme <duplicate-id>`, after the JSON pull) → QA on the duplicate's preview → **publish from the admin**. Rollback = publish the previous live theme, which you never touched.
4. Merchant edits now live *only* in the theme, not in Git: the runbook's first step on every task becomes `shopify theme pull --live` and a commit — that's your only record of what changed in the editor.

Write `docs/deploy-runbook.md` with both paths as numbered checklists, the backup naming convention, the library-cap cleanup rule, and the rollback sequence including the "re-publish the connected theme" step. Add `notes/theme-workflow-card.md` (one page: the state model table, the four JSON rules, the flow) to the handbook.
