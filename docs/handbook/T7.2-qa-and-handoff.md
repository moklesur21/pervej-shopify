# T7.2 — QA & Handoff
**Module 7 · Tutorial 25 of 26 · Est. 4–5 hours**

**Goal:** Run the full house QA checklist on an earlier build as if an agency were paying for it, log and fix real defects, record the handoff Loom, and write the handoff package — then sign it off against the definition of done. You leave with the **Shopify QA checklist**, the **handoff template** and the **delivery card** that every future delivery reuses.

**Prerequisites:** T7.1's deploy runbook (this tutorial is steps 5, 8 and 13 of that flow done properly). A build to QA — the T7.1 change request on the dev store is ideal (built recently, not yet independently checked); the T2.3 cart drawer works too. A real Android or iOS device, a Loom account (or the free alternative from the tools list), and strategy doc **Sections 8.3–8.5** open.

---

## 1. Concept

### 1.1 QA is a separate act from building

Builders can't QA their own work in the same sitting — the eye follows the path it built. Two rules make the pass real:

- **Fresh eyes.** QA happens after a break, ideally the next day, from the checklist, not from memory of what you built.
- **No known-defect passes.** A defect you know about and ship anyway is the two-regression rule spent on purpose. Fix it, or descope it *in writing* with the agency's agreement before delivery. There is no third option.

AI-assisted builds raise the stakes, not lower them: Claude Code output arrives *looking* finished — consistent naming, tidy comments, plausible edge-case handling — which is precisely what switches a reviewer's attention off. The review protocol caught what's wrong *in the code*; QA catches what's wrong *in the store*: the setting that doesn't survive a save, the drawer that traps focus on iOS, the app block that quietly vanished.

### 1.2 The house checklist, Shopify edition

Strategy doc 8.3 is the floor. Each item below has a **how** and an **evidence** column because the evidence *is* the deliverable: an agency should never have to trust you, only look.

| # | Check (8.3 item) | How, on Shopify | Evidence |
|---|---|---|---|
| 1 | Functional pass on scoped items + edge cases | Test every deliverable from the written scope. Edge cases from the spec plus the standard Shopify set: empty metafield, sold-out variant, single-image product, 80-character title, product with no compare-at price, collection with 1 product, logged-in vs logged-out | Screenshots per case, named `01-functional-{case}.png` |
| 2 | Full purchase flow with a test order | Add to cart → cart/drawer → checkout → order placed → order visible in admin. **Dev store:** Shopify's test gateway with its documented test card numbers (success, decline, exception). **Client live store:** never flip Shopify Payments test mode without the agency's explicit go — it blocks real checkouts while on. Default: a low-value real order with a 100% discount code, tagged `test`, cancelled and refunded after | Order number + admin screenshot; the discount code name if used |
| 3 | Theme editor pass | Open the preview theme in the editor: exercise every setting and block you added, min/max block counts, presets, empty states; save; reload; confirm it stuck. Try to break it as a non-technical merchant would | Short screen recording or 3–4 screenshots |
| 4 | App blocks and embeds still render | List the store's app blocks/embeds *before* the change; confirm each still renders after. A section rewrite can drop an app block without any error | Before/after list in the QA log |
| 5 | Mobile: 360 / 390 / 768 + a real device | DevTools at the three widths, then the real phone: touch targets, sticky elements, safe areas, drawer scroll-lock, keyboard covering inputs | Device screenshots; note the OS/browser versions |
| 6 | Cross-browser: Chrome, Safari, Firefox, iOS Safari | Safari is where web components, `dialog`, `:has()` and scroll-locking break. iOS Safari counts separately from desktop Safari | One screenshot per browser of the feature |
| 7 | Linters clean | `shopify theme check` — zero errors; warnings triaged and either fixed or listed. Push used `--strict` | Terminal output |
| 8 | No hardcoded user-facing strings | Every merchant-visible string in `locales/en.default.json`, every setting label in `en.default.schema.json`. Prices via money filters. If the store has Markets, preview in a second locale/currency | `grep` results; second-locale screenshot |
| 9 | No console errors; no Liquid errors | Console clean on home, collection, product, cart, checkout. `curl` the preview page and grep for `Liquid error` — it renders as visible text, which merchants screenshot first | Console screenshot; grep output |
| 10 | Lighthouse before/after — no regression | Mobile, same three pages (home, collection, product), **three runs each, take the median**, before and after. Same theme settings, same cache state | Two screenshot sets, medians in a table |
| 11 | Cart/checkout scripts unbroken | Through the test order: pixel/GA4 events fire (T5.1 verification), upsell blocks render, shipping calculator returns rates, discount codes apply, cart drawer events still dispatch (T2.3) | Pixel debug screenshot; event list |
| 12 | Accessibility floor | Keyboard: reach, operate and leave every interactive element; focus visible; `Esc` closes drawers/modals and returns focus; sensible `aria-*` on custom components; contrast; alt text. Lighthouse accessibility ≥ 90 | Lighthouse a11y score; note any keyboard trap found |
| 13 | Store-state variants | Customer logged in and out; B2B/company context if the store uses it (T6.1); each Market if enabled | Screenshots per state that applies |
| 14 | Structured data intact | Validator on a product page — one Product entity, valid JSON (T6.2) | Validator screenshot |
| 15 | No debug leftovers | `console.log`, `{{ … \| json }}` dumps, `TODO`, lorem, placeholder images or copy left in settings | `grep` output; a look at the settings |
| 16 | Backup exists; rollback path confirmed | Backup theme named per convention; you know the publish-to-roll-back sequence (T7.1) | Backup theme name in the log |
| 17 | Scope diff clean | `git diff --stat main..feat/…` shows only in-scope files | Diff stat pasted |
| 18 | Loom recorded | Section 1.4 structure | The link |

Items 3, 4, 8, 9's Liquid grep, 13 and 14 are the Shopify-specific additions to the house list — they're the ones a Woo developer's instinct won't reach for.

### 1.3 Defect discipline

Every defect gets a log line: **ID · severity · steps · expected vs actual · evidence · fix commit · re-test result.** Severity: **S1** blocks purchase or breaks the live theme · **S2** scoped feature wrong · **S3** minor/visual · **S4** cosmetic. S1–S2 always block delivery; S3–S4 block unless descoped in writing.

**A fix is a change, and changes regress.** After any fix: re-run the checks the fix could touch, *and* the purchase flow (#2) again. The purchase flow is the one check that's never skipped on a re-test, because it's the one the merchant will feel first.

### 1.4 The Loom — agencies buy the reasoning

Three to five minutes, recorded on the **preview theme**, clean browser profile, no admin secrets or personal tabs on screen. The structure:

1. **The brief, restated** (15 s) — "You asked for X and Y; nothing else was to change."
2. **The feature working** (60–90 s) — desktop, then the real phone (hold it up, or screen-mirror). Show an edge case deliberately.
3. **How the merchant edits it** (45 s) — theme editor: the settings, the blocks, what happens when a field is left empty.
4. **What was checked** (45 s) — show, don't claim: the test order in admin, the Lighthouse before/after medians, the device shots, "Theme Check clean."
5. **Limits, next steps, warranty** (20 s) — what's out of scope, the backup theme name, "14-day warranty starts on deploy."

White-label rules apply on tape: the agency's name, never ours; "the team" or "we," never a personal brand; **never a word about AI or Claude** (rule 1 of the offer). Title the recording with the task name; unlisted link. Watch it back before sending — the first take always says something it shouldn't.

### 1.5 The handoff package

`docs/handoff-{task}.md`, written in the agency's voice, sent through their channel (Slack, ClickUp, Trello — theirs, not ours):

1. **Summary** — two sentences: what was asked, what was delivered.
2. **What changed** — files touched (from the diff stat), theme settings added, metafields defined, any app or store-setting change made live and when.
3. **How to use it** — merchant steps in the theme editor, with one screenshot.
4. **QA evidence** — the checklist with links to the evidence folder; before/after numbers in a small table.
5. **Known limitations / out of scope** — stated plainly; this is where change orders come from later, politely.
6. **Backup and rollback** — backup theme name; "publish it to revert instantly."
7. **Warranty** — start date, end date, what it covers (defects in the scoped work).
8. **Next** — optional, one line, only if genuinely useful ("the same block could carry a 'complete the look' bundle if the client wants it").

### 1.6 Definition of done (8.5, made checkable)

Scoped items delivered · QA checklist 100% with evidence · staging approved, or the 5-business-day window elapsed · deployed with backup · handoff package and Loom sent · warranty clock started. **Done is a state the agency can verify by looking, not a feeling you have about the work.** If any line can't be pointed at, it isn't done.

### 1.7 Warranty triage

- **Warranty bug:** a defect in the scoped work, surfaced after deploy → fixed at our cost, same runbook (branch, preview, backup, deploy), response inside the retainer SLA.
- **Revision:** an edge case surfaced *during staging review* → normal, not a strike.
- **Change request:** new behaviour, new scope, "while you're in there" → written change order, priced.
- **Not ours:** app updates, theme-editor changes by the merchant after handoff, other vendors' work → diagnosed once as a courtesy, then quoted. The Git history and the bot's commits (T7.1) tell you exactly which it is — say so kindly, with the evidence.

### 1.8 Woo bridge

| Woo | Shopify | Where it breaks |
|---|---|---|
| PHP errors in `debug.log`, hidden from visitors | Liquid errors render **on the page** as text | Merchants see them before you do; grep the rendered HTML |
| Plugin-conflict check before handoff | App block / app embed render check | Apps live inside the theme's sections; your edit can remove them silently |
| PHPCS / WPCS clean | `shopify theme check` clean; `--strict` on push | Same idea; the linter also knows Liquid performance and schema rules |
| Test order via Woo test mode, COD, or a sandbox gateway; harmless on staging | Test gateway on dev stores; **Shopify Payments test mode blocks real checkouts** on a live store | Test orders on live stores need an agreed procedure, not a toggle |
| QA on a staging server with a DB copy | QA on the preview theme against **live data** | You're testing with the merchant's real products — good — but nothing you save in the admin is staged |
| Query Monitor for slow queries | Theme Inspector / Lighthouse for slow Liquid and payload | No server-side profiler; performance QA is page-level |
| i18n via `__()` and `.po` files | Locale JSON + schema locale JSON; Markets previews | Two files per language, and setting labels are translatable too |
| Customizer changes are theme mods in the DB | Theme editor changes are commits (if connected) and JSON files | QA the editor path as a first-class surface — it's part of the code |

## 2. Claude Code drill — a paid-grade QA pass on your own work

### Drill A — Build the checklist file *(hand-written, then challenged)*

1. Create `docs/qa-checklist.md` from the 18 items in Section 1.2, with the **how** and **evidence** columns, and a header block for task name, build, tester, date, theme ID, backup theme name.
2. Only then: paste it into Claude Code and ask *"What does a senior Shopify QA reviewer check that this list misses, for a theme-code delivery?"* Accept an addition only if you can verify it and it earns its evidence column. Reject anything generic. Log what you accepted and rejected — the rejections teach you as much as the additions.

### Drill B — Plant the defects *(so the pass is real)*

On a throwaway branch off the build (`qa-drill/planted`), ask Claude Code to **introduce four subtle defects without telling you which**, from this menu: a hardcoded user-facing string; a mobile-only overflow at 360px; a setting whose value doesn't persist after save; a `console.log` left in; a Liquid error on the empty-metafield case; an app block dropped from a section; a focus trap in a drawer. Push it as an unpublished preview theme. Don't look at the diff. (This mirrors W1.6's planted-bug method in the WooCommerce series, `pervej-woo` — tools, not guesswork.)

### Drill C — Run the pass

Work `docs/qa-checklist.md` top to bottom against the planted theme. Capture evidence into `qa/{task}/`, one file per check, named by number. Non-negotiables:

- The **test order** through the test gateway, then found in admin — screenshot the order.
- The **theme editor pass** — try to break your own settings the way a merchant would.
- The **app block list** before/after.
- **Three-run Lighthouse medians** on the same three pages, before (main) and after (planted branch).
- The **Liquid error grep** on the rendered preview.
- The **keyboard pass** with the mouse unplugged (literally — unplug it).
- The **real phone**.

Log every defect in `qa/{task}/defects.md` with the Section 1.3 fields. You should find all four plants; if you find fewer, the checklist has a hole — fix the *checklist*, then re-run. If you find more than four, congratulations: those are real.

### Drill D — Fix and re-test

Fix on the branch, one defect per commit, referencing the defect ID. After each fix: re-run the affected checks **and the purchase flow**. Update the log with the re-test result. Finish with a scope diff (#17) and Theme Check (#7) on the final state. Delete the planted branch and its preview theme when done; the log stays.

### Drill E — Optional CI floor

For repos we own (or where the agency allows a custom app token): add `.github/workflows/ci.yml` with `shopify/theme-check-action` and `shopify/lighthouse-ci-action` (custom app with `read_products` + `write_themes`; store, token, and store password in secrets; performance and accessibility minimums set). It runs on every push and fails the PR below threshold. This automates checks #7, #10 and #12's score — nothing else. It is a floor, not the pass; note that in the runbook so it never becomes an excuse to skip the rest.

### Drill F — Record the Loom

Record the handoff walkthrough for the *fixed* build using the 1.4 structure. Watch it back. Re-record once, because you'll hear yourself say "I" or explain the tool instead of the result. Save the link into the handoff package.

### Drill G — Handoff and sign-off

1. Write `docs/handoff-{task}.md` per Section 1.5 — agency voice, evidence links, backup theme, warranty dates.
2. Write the Slack-style delivery message (four lines: what's delivered, preview link, Loom, what you need from them and by when — the 5-day window).
3. Walk the definition of done (1.6) line by line and mark each with where the evidence is. If a line can't be pointed at, it isn't done — go back.
4. Add `notes/delivery-card.md` to the handbook: the 18 checks by name, the severity rules, the Loom structure and the definition of done on a single page. This card and T7.1's workflow card together are the whole delivery standard.

## 3. Verification checklist

- [ ] `docs/qa-checklist.md` written by hand with how/evidence columns; Claude Code's additions accepted/rejected with reasons logged
- [ ] Four defects planted blind; all four found by the checklist (or the checklist repaired and re-run)
- [ ] Evidence folder complete: one artifact per check, numbered
- [ ] Test order placed through the test gateway and located in admin
- [ ] Theme editor pass done; app block/embed list before and after
- [ ] Real-device shots (Android or iOS) with versions noted; all four browsers covered
- [ ] Theme Check zero errors; warnings triaged; Liquid-error grep clean; console clean on five page types
- [ ] Lighthouse three-run medians, before and after, three pages, tabled — no regression
- [ ] Pixel/GA4 events verified through the test order; shipping rates and a discount code confirmed
- [ ] Keyboard pass completed; `Esc` closes and returns focus; a11y score ≥ 90
- [ ] Defect log complete: severity, steps, evidence, fix commit, re-test; purchase flow re-run after every fix
- [ ] Scope diff clean; backup theme named in the log
- [ ] Loom recorded to the 1.4 structure; watched back; no personal brand, no AI mention
- [ ] Handoff package and delivery message written; definition of done walked with evidence pointers
- [ ] `notes/delivery-card.md` added to the handbook

## 4. Done when

All boxes ticked **and** you can answer out loud, without looking:

1. Why does an AI-assisted build make the QA pass *more* necessary, not less?
2. Name the six checks on the Shopify list that a Woo developer's instinct won't reach for, and why each exists.
3. The agency wants a test order on the client's live store. What do you never do, and what do you propose instead?
4. A fix is a change — what do you re-run after every fix, and which check is never skipped?
5. Recite the Loom structure and the three white-label rules for it.
6. "Is it done?" — give the six-line answer and say where the evidence for each line lives.
7. Post-deploy, the merchant reports the feature "broke." How do you decide between warranty bug, change request and not-ours — and what shows you which?
