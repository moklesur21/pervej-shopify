# T1.4 — Section Groups & Nested Theme Blocks
**Module 1 · Tutorial 7 of 26 · Est. 3–4 hours**

**Goal:** Master the two architectures that live *around* T1.3's sections: **section groups** (the merchant-composable header/footer areas) and **theme blocks** (reusable, nestable blocks in their own files — the architecture Horizon is built on). By the end you'll have extended the header the way clients actually request it, and shipped a nested-block layout.

**Prerequisites:** T1.3 complete — schema fluency is assumed from here on.

---

## 1. Concept

### A. Section groups — the areas outside templates

T1.2 taught you that templates control the middle of the page. The header and footer live in **group files** instead — JSON in the `sections/` folder:

```json
// sections/header-group.json (Dawn's, simplified)
{
  "type": "header",
  "name": "Header group",
  "sections": {
    "announcement-bar": { "type": "announcement-bar", "settings": { … } },
    "header":           { "type": "header",           "settings": { … } }
  },
  "order": ["announcement-bar", "header"]
}
```

Same shape as a JSON template — sections, settings, order — but rendered from the **layout**:

```liquid
{% sections 'header-group' %}   ← plural tag: renders a whole group
{% section  'some-section' %}   ← singular tag: renders ONE static section
```

Don't confuse the two — the one-letter difference matters in review.

What groups buy you: merchants can **add, remove, and reorder sections inside the header and footer areas** in the editor — announcement bars, utility strips, banners — without touching layout code. Three group types exist: `header`, `footer`, and `aside` (for drawers/overlays). And the now-familiar rule applies: merchant edits to a group are written into **that group's JSON file** — shared state, captured with the same pull-diff-decide habit.

### B. The block family tree

You've met one kind of block. There are three:

| | **Section blocks** (T1.3) | **Theme blocks** | **App blocks** |
|---|---|---|---|
| Defined in | The section's own `{% schema %}` | Own `.liquid` file in **`/blocks`** folder, with its own `{% schema %}` | The app's code (T5.3) |
| Reusable across sections | ✗ | ✓ | ✓ |
| Can nest children | ✗ | ✓ — up to **8 levels** deep | ✗ |
| Editor picker needs | listed in section schema | its own **`presets`** (like sections) | app installed + `@app` support |

**A theme block file** looks like a mini-section:

```liquid
{% doc %} blocks/badge.liquid {% enddoc %}
<span class="badge badge--{{ block.settings.style }}">{{ block.settings.text }}</span>

{% schema %}
{
  "name": "Badge",
  "settings": [
    { "type": "text", "id": "text", "label": "Text", "default": "New" },
    { "type": "select", "id": "style", "label": "Style",
      "options": [ { "value": "solid", "label": "Solid" }, { "value": "outline", "label": "Outline" } ],
      "default": "solid" }
  ],
  "presets": [{ "name": "Badge" }]
}
{% endschema %}
```

By default Shopify **auto-wraps** each theme block in a `<div>` that carries the editor attributes. If your markup needs to own its root element, set `"tag": null` in the schema — then the block must have exactly one top-level element and *you* must put `{{ block.shopify_attributes }}` on it.

**A section (or block) accepts theme blocks** with two moves — schema opt-in plus a render point:

```liquid
{% content_for 'blocks' %}     ← children render here, in editor order

{% schema %}
{ "name": "Flexible content", "blocks": [{ "type": "@theme" }, { "type": "@app" }], … }
{% endschema %}
```

`@theme` accepts *all* theme blocks; list specific types instead (or alongside) to restrict or to highlight recommended ones in the picker. **Nesting** is just a theme block doing the same thing: its schema accepts blocks, its markup calls `{% content_for 'blocks' %}` — turtles, 8 levels down.

**The law of the land (verified, current):** a single section accepts **either** theme blocks **or** section blocks — never both. You'll collide with this rule on purpose in the drill.

Two more facts for scale: a theme can hold at most **300 theme blocks** (every file in `/blocks` counts), and there's also `{% content_for 'block', type: '…', id: '…' %}` for rendering one *specific* block statically — think "a snippet with merchant settings."

**Why this architecture is career-relevant:** Horizon themes are built almost entirely from theme blocks — that's what makes them page-builder-flexible while staying platform-native. And merchants on supporting themes can now generate theme blocks with Sidekick (AI) straight into `/blocks`. Client themes will contain this architecture whether or not you put it there — you need to read it fluently either way. T1.6 completes the Dawn-vs-Horizon picture.

## 2. Woo bridge

| You know (Woo) | Here (Shopify) | Where the mapping breaks |
|---|---|---|
| `get_header()` / `header.php` | `{% sections 'header-group' %}` in the layout | The header's *composition* is merchant-editable data, not code |
| Widget areas (`register_sidebar`) in header/footer | Section groups | Closest match yet — but only three group types exist, rendered only where the layout calls them |
| Block theme `parts/header.html` | `sections/header-group.json` | Same idea, JSON instead of markup |
| **Gutenberg `InnerBlocks`** | **Nested theme blocks + `{% content_for 'blocks' %}`** | *The* bridge for this tutorial — server-rendered, no React, capped at 8 levels |
| Reusable blocks / synced patterns | Theme blocks in `/blocks` | Define once, drop into any accepting section |
| `block.json` per block | The block's own `{% schema %}` | Same single-source-of-truth instinct |
| "Anything can nest anything" | Exclusivity rule + depth cap + 300-block cap | The platform fences flexibility; knowing the fences is the expertise |

## 3. Claude Code drill

Branch: `git checkout -b t1-4-groups-and-blocks`.

### Part A — Dissect the header group (20 min, no AI)

1. Open `sections/header-group.json` — map its `type`, `sections`, `order` against what you see on the storefront.
2. Open `layout/theme.liquid` — find the `{% sections 'header-group' %}` and `{% sections 'footer-group' %}` calls. Note there's no header markup in the layout at all.
3. In the theme editor, click into the **Header** area in the left sidebar tree — see the same composition, live.

### Part B — Extend the header like a client would ask

The request you'll get a dozen times: *"Can we add our phone number and hours above the header?"*

1. Build `sections/utility-bar.liquid` — mostly by hand, it's small; this is T1.3 muscle memory. Settings: phone (`text`) + phone link (`text`, holds a `tel:` value), email (`text`), hours (`text`), color scheme. Each item renders only when `!= blank`. One schema extra you haven't used yet:
   ```json
   "enabled_on": { "groups": ["header"] }
   ```
   — this section exists *only* for the header area; it won't appear in the picker anywhere else.
2. In the editor, add **Utility bar** to the Header group, dragged above the announcement bar. Save.
3. Capture it:
   ```bash
   shopify theme pull --development --only "sections/header-group.json"
   git diff sections/header-group.json
   ```
   Read the diff — your section, the merchant's placement, one JSON file — then commit.

### Part C — The nested-block layout

Now the theme-block build. Three files; **you spec the schemas by hand first** (they're short), AI builds to spec:

- **`blocks/badge.liquid`** — the leaf. Settings: text, style (`select`: solid/outline). Preset. No children.
- **`blocks/stack.liquid`** — the container. Settings: direction (`select`: horizontal/vertical), gap (`range`, px), alignment (`text_alignment`). Accepts children: schema `"blocks": [{ "type": "@theme" }]`, markup renders `{% content_for 'blocks' %}` inside a flex wrapper driven by the settings. Preset.
- **`sections/flexible-content.liquid`** — the host. Accepts `@theme` (and `@app`), renders `{% content_for 'blocks' %}`, wrapped in your standard padding + color-scheme pattern from T1.3.

Prompt Claude Code with your three schemas and the house standards; add one requirement worth watching: *"Use the default block wrapper unless the markup requires `tag: null` — if you use `tag: null`, say why."* Then run the **full review protocol** — hunt specifically for: presets present on both blocks (no preset = invisible in the picker), `content_for 'blocks'` placed where children should actually land, and no invented schema attributes.

**Then play, as the merchant:** add Flexible content to the homepage → add a Stack → put two Badges inside it → put *another Stack inside the Stack* with its own Badges → watch the sidebar tree nest → drag to reorder at every level. That's InnerBlocks, server-rendered.

### Part D — Collide with the exclusivity rule

In `flexible-content`'s schema, add a local block type alongside `@theme`:

```json
"blocks": [{ "type": "@theme" }, { "type": "quote", "name": "Quote", "settings": [] }]
```

Run `shopify theme check` and reload the editor — read the error, feel the fence, revert. Then write the decision note in `notes/blocks-decision.md`: *classic/Dawn-style client themes → section blocks (T1.3); Horizon-style or new flexible builds → theme blocks (T1.4); never both in one section.* You'll cite this note in real scoping calls.
