# T1.2 — Theme Anatomy
**Module 1 · Tutorial 5 of 26 · Est. 3–4 hours**

**Goal:** Know exactly how a Shopify page assembles itself — which of the seven folders does what, why templates are *data* while sections are *markup*, and who else writes to your files (spoiler: the merchant). You'll trace a product page's full render path, then alter it at three different layers.

**Prerequisites:** T1.1 complete. `shopify theme dev` running throughout.

---

## 1. Concept — seven folders, one assembly line

```
dawn-playground/
├── layout/      theme.liquid — the master wrapper around every page
├── templates/   one file per page type — mostly .json manifests, not markup
│   └── customers/   account pages (login, orders, addresses…)
├── sections/    the building blocks — .liquid markup + {% schema %}
├── blocks/      (optional) standalone theme blocks — T1.4's topic
├── snippets/    {% render %} partials — no schema, invisible to the editor
├── assets/      CSS, JS, images — one flat folder, no subdirectories
├── config/      settings_schema.json (theme-settings UI) · settings_data.json (saved values)
└── locales/     en.default.json (storefront strings, the `| t` source)
                 en.default.schema.json (editor-label translations)
```

**The render path.** When a request hits `/products/aurora-mug`:

1. Shopify resolves the page type → `product` → loads **`templates/product.json`**.
2. That JSON is a **manifest, not markup**: which sections render, in what order, with what settings and blocks. The markup lives in the section files it names — here, `sections/main-product.liquid`.
3. Each section renders its Liquid, loops its **blocks**, and `{% render %}`s any **snippets** it needs.
4. The whole result is injected into **`layout/theme.liquid`** at `{{ content_for_layout }}`.

Two non-negotiables inside `theme.liquid`:

- **`{{ content_for_header }}`** — Shopify's injection point in `<head>`: platform scripts, app embeds, analytics, the editor runtime. Your `wp_head()`. **Never remove or move it.**
- **`{{ content_for_layout }}`** — where the page goes. Your `the_content()`-of-everything.

**Who writes JSON, and when.** This is the part that changes how you work:

- Merchant customizes a page in the theme editor → Shopify writes into **that template's `.json`** (section settings, block order, everything).
- Merchant changes theme settings (colors, typography) → Shopify writes **`config/settings_data.json`**.
- You edit files locally → the CLI syncs them up.

So template JSONs and `settings_data.json` are **shared state between you and the merchant** — the same files, written from both sides. On client work this is why diffs of a pulled theme are full of JSON churn you didn't create, and why the pull → diff → commit habit you'll build today matters.

**One workflow warning, verified against current CLI behavior:** each `shopify theme dev` run **replaces** the development theme with your local files. Changes made in the *editor* on a dev theme are disposable unless you deliberately bring them down — either run dev with `--theme-editor-sync`, or (our house preference, more explicit) pull them:

```bash
shopify theme pull --development --only "templates/product.json"
```

Local files + Git are the source of truth. Editor experiments get pulled in on purpose, or they die with the dev theme.

**Alternate templates** — the quiet superpower: `templates/product.spotlight.json` creates a second product layout, assignable to individual products in the admin (product page → *Theme template*). Per-product layouts with zero code duplication — what took a custom `single-product-{slug}.php` dance in Woo is a config file here.

## 2. Woo bridge

| You know (Woo) | Here (Shopify) | Where the mapping breaks |
|---|---|---|
| `single-product.php` → `content-single-product.php` | `templates/product.json` → `sections/main-product.liquid` | The template is **data**; markup is one level down |
| `archive-product.php` | `templates/collection.json` → `sections/main-collection-product-grid.liquid` | Same split |
| `header.php` / `footer.php` + `wp_head()` / `wp_footer()` | `layout/theme.liquid` + `content_for_header` | One wrapper file; header/footer are *section groups* (T1.4) |
| Template hierarchy magic (file-name cascade) | Explicit: page type → its template JSON | No cascade to memorize; alternates are named suffixes, assigned in admin |
| `get_template_part()` | `{% render 'snippet' %}` | Isolated scope (T1.1) — and snippets never appear in the editor |
| Customizer + widget areas | Theme editor + sections/blocks | The editor is the merchant's primary tool, and it **writes to your repo's JSON** |
| `is_product()`, `is_cart()`, conditional tags | `{{ request.page_type }}` | One object, string values — you'll prove it in the drill |
| `style.css`, `functions.php` inside the theme | `assets/` + no PHP anywhere | Assets referenced via `{{ 'base.css' \| asset_url \| stylesheet_tag }}` |
| Child theme overrides | Don't exist — the theme copy is already yours | "Which file do I override?" becomes "which file *is it*?" |

**First instinct to retrain:** *"change the product page"* ≠ open `templates/product.json`. That file tells you **which section** to open. The JSON is the table of contents; the section is the chapter.

## 3. Claude Code drill — trace it, then alter it at three layers

Branch first: `git checkout -b t1-2-anatomy`.

### Part A — The trace

1. Ask Claude Code for the map:
   > "Trace the render path of the default product page in this theme, starting from `templates/product.json`. List every file involved in order — template, sections, snippets, layout — and one line on each file's role. Don't modify anything."
2. **Walk the territory yourself.** Open each file it named, in order:
   - `templates/product.json` — read the manifest: find the `main-product` entry, its `blocks`, and the `order` array at the bottom.
   - `sections/main-product.liquid` — scroll to the `{% schema %}` at the bottom first, then find where blocks render (the `{% case block.type %}` structure). Find the **price** block case — it renders the `price` snippet you dissected in T1.1. Full circle.
   - `layout/theme.liquid` — locate `content_for_header`, `content_for_layout`, and where `base.css` loads.
3. Write the diagram into `notes/render-path.md` in the repo — URL → template → sections → snippets → layout, in your own words. Your repo starts accumulating your own handbook today; correct anything the AI map got wrong while you're at it.

### Part B — Alter the page at three layers

**Layer 1 — Template (data).** Create the alternate template:

1. Copy `templates/product.json` → `templates/product.spotlight.json`.
2. Edit the copy by hand: add one more section entry (Dawn's `multicolumn` is easy) and put it in the `order` array. Hand-editing this JSON once teaches you its shape better than any diagram.
3. In the admin, open **one** product → set *Theme template* → `spotlight`. Verify: that product shows the extra section; every other product doesn't.

**Layer 2 — Editor (the merchant's pen).** Prove who else writes your files:

1. In the theme editor (on your dev theme), open the **default** product template and add any section from the picker. Save.
2. Your local `templates/product.json` hasn't changed — the edit lives on the dev theme. Bring it down:
   ```bash
   shopify theme pull --development --only "templates/product.json"
   git diff templates/product.json
   ```
3. Read the diff: settings, block IDs, order — the editor is just another author committing JSON. Keep the change or `git checkout` it away; the point is you now *choose*, deliberately, every time. On client work this exact pull-diff-decide move is how merchant edits and your code coexist.

**Layer 3 — Layout (everything at once).** In `layout/theme.liquid`, just before `</head>`, add:

```liquid
<!-- t1.2 page_type: {{ request.page_type }} -->
```

View source on the homepage, a product, a collection, the cart, and a nonsense URL: `index`, `product`, `collection`, `cart`, `404` — one wrapper around every page, and there's your `is_*()` replacement as live data. Then **remove the line** — debug lines don't get committed.

### Bonus tool — the Liquid REPL

```bash
shopify theme console
```

An interactive Liquid prompt evaluated against your dev store — try `product.title` on a product URL context, or `{{ 2450 | money }}`. Your WP-CLI shell equivalent; remember it exists next time you're unsure what an object holds.
