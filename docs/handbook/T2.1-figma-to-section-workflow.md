# T2.1 — The Figma → Section Workflow with Claude Code
**Module 2 · Tutorial 10 of 26 · Est. 4–5 hours (includes your first full production rep)**

**Goal:** Install the production method — how a real agency deliverable travels from a Figma link to a QA'd, merchant-proofed, committed section. Module 1 gave you the platform; this tutorial gives you the assembly line. It ships with three reusable templates you'll use on actual client work.

**Prerequisites:** Module 1 complete. A free Figma account (figma.com) — sign up before starting.

---

## 1. Concept — the five-stage method

Nothing here is new platform knowledge. It's *sequence and discipline* — the difference between "I can build sections" and "I deliver sections on quote, on time, twice a week." The stages:

```
0 Intake → 1 Read → 2 Extract → 3 Build loop → 4 Merchant-proof & QA → 5 Package
```

### Stage 0 — Intake (5 min)

What arrives from an agency: a Figma link, maybe brand assets, a one-line brief. Before anything else, check:

- Desktop **and** mobile frames exist? (Missing mobile = you'll infer it — that's an *assumption to state*, not a guess to hide.)
- States designed — hover, empty, long-text? Usually not. More assumptions to state.
- Fonts and colors: do they map to the theme's existing settings, or is the design introducing new ones? (New fonts = loading cost + licensing question — flag early.)
- Anything moving? Carousels, animation, tabs → that's JS scope (T2.2). Price and plan it separately; don't let it sneak into a "section" quote.

Two minutes of checking here prevents the classic mid-build scope surprise.

### Stage 1 — Read the design like a developer (20–30 min)

This stage produces the **build spec** — the most senior artifact in the whole method. Three reads of the frame:

1. **Structure read:** boxes and rhythm. What's the layout skeleton — grid? columns? What's the spacing system (one base unit repeated, or chaos)? What repeats? **Anything that repeats is a block.**
2. **Theme-mapping read:** every color → an existing color scheme, or new? Type sizes → the theme's scale? Buttons → the theme's button classes? The professional default is **map to what exists** — a section that imports its own parallel styling is bloat you'll be asked to remove in Module 3.
3. **Schema read:** T1.3's discipline, applied to a picture. Everything a merchant could plausibly want to change becomes a setting; every repeating unit becomes a block with its own settings. Write the schema *before* any code exists.

The output goes in the build-spec template (Section 3, Template 1) — including the **assumptions list**. Sending that list back to the agency before building is what senior looks like from the outside.

### Stage 2 — Extract (10–15 min)

- **Screenshot the frames** — desktop and mobile. These are your build reference *and* they go straight into Claude Code: paste the screenshot into the session so the model sees what you see. The screenshot-plus-spec method works with any Figma access level.
- **Export assets:** images at 2×, icons as SVG. Compress before they enter the theme (Module 3 will make you regret every 800 KB hero).
- **Note exact values** for the load-bearing numbers: section padding, gap, heading size, max-width. If the agency's plan gives you Dev Mode, its measurements are handy and its generated CSS is *reference, not gospel* — same rule as every AI output. (Where Dev Mode access exists, Figma's MCP server can pipe design context straight into Claude Code — worth configuring when you have it; never depend on it.)

### Stage 3 — The build loop

One well-specified prompt lands ~80% of a section; iteration closes the rest. The rhythm:

1. **Master prompt** (Template 2): your hand-written schema + the screenshot + exact values + the house-standards block. One complete, *scoped* ask — never "build me this design" with a bare image.
2. **Review protocol** on the output — full T0.3 pass, plus the S3-specific hunt: did it reuse the theme's existing classes and CSS variables, or invent a parallel style system? Parallel systems get rejected in review.
3. **The gap list:** preview and screenshot side by side. List concrete deltas — "card gap is 24px, design shows 32" · "heading weight too light" · "mobile should stack image above text." Specific gaps become specific iteration prompts. **Never prompt "make it closer to the design"** — that's asking the model to guess which of forty properties you mean.
4. Iterate in small diffs until the gap list is empty at desktop and mobile widths.

What "matches the design" means professionally: spacing rhythm, type scale, alignment, and hierarchy read the same. Not pixel-identical across every browser — agencies don't expect that; they expect *nothing looks off*.

### Stage 4 — Merchant-proof & QA (20 min)

- The T1.3 merchant test: empty settings, long text, block reorder, two instances on one page.
- Breakpoints from the delivery checklist: **360px, 390px, 768px**, plus desktop. Devtools first, real phone when it matters.
- `shopify theme check` clean · zero console errors · images sized and lazy-loaded (`image_tag` handles `srcset`; below-the-fold gets `loading: 'lazy'`).
- 60-second Lighthouse sanity: the section must not tank the page. (Full performance discipline is Module 3; the habit of *looking* starts now.)

### Stage 5 — Package (10 min)

A delivery isn't code, it's code **plus the ability to use it**: preview access, a summary of what changed, how the merchant edits it, and the assumptions you made (Template 3). On real work a Loom walkthrough joins this — T7.2 trains that; leave a placeholder line in the notes for now.

**Time target:** with fluency, a section of the drill's size lands in **2–4 hours end to end**. Rep #1 today will take longer. That's what reps are for.

## 2. Woo bridge

| You know (Woo) | Here (Shopify) | Where the mapping breaks |
|---|---|---|
| PSD/Figma → custom page template or ACF flexible-content layout | Figma → section + schema | Schema decomposition comes **first**, not as an afterthought — merchant-editability *is* the deliverable |
| Zeplin/Avocode/Dev-Mode handoff values | Same — reference, not gospel | Unchanged instinct, new toolchain |
| "Use the theme's existing styles, don't ship your own Bootstrap" | Reuse Dawn's classes, variables, button styles | Same discipline, now enforced in review |
| Client sees the front end; your code hides behind PHP | Everything you ship is theme-editor-visible | The merchant *will* open your section and touch every setting — build for that audience |
| Handoff = "it's live" | Handoff = preview + settings docs + assumptions | The packaging is part of the product |

## 3. The three templates

Copy these into your repo under `notes/templates/` today; refine them for life.

### Template 1 — Build spec (`build-spec.md`)

```markdown
# Build spec — [section name]
Figma: [link] · Frames: desktop ✓ / mobile ✓|✗ · Date: [date]

## Structure
- Layout skeleton: [e.g., 2-col 50/50, image left / stacked on mobile]
- Spacing base: [e.g., 8px rhythm; section pad 64/40]
- Repeating unit: [e.g., feature card ×3] → block type: [name]

## Theme mapping
- Colors → [scheme-1 / new value?] · Type → [existing scale / new]
- Buttons → [theme button classes] · Container → [page-width]

## Schema (hand-written)
[settings + blocks with type/id/label/default — full JSON]

## Responsive story
[what changes at <750px — from design or inferred]

## Assumptions & questions for the agency
1. [Mobile layout inferred as stacked — confirm.]
2. [Hover states not designed — using theme defaults.]
```

### Template 2 — Master build prompt

```text
Build `sections/[name].liquid` for this Dawn-based theme.

Design: [screenshot pasted]. Key measurements: [pad 64px desktop/40 mobile,
gap 32px, heading 40px/1.1, max-width = theme page-width].

Schema — use exactly this: [paste your JSON].

Requirements:
- Repeating unit renders from blocks with {{ block.shopify_attributes }}.
- Reuse this theme's existing CSS variables, button classes, and page-width
  container — do not invent parallel styles.
- Blank-guard every optional setting (`!= blank`).
- Images via image_url + image_tag, sized, lazy below the fold.
- Scoped section-padding pattern; color via the theme's scheme classes.
- Mobile (<750px): [your responsive story].
- Theme Check clean. Smallest complete implementation.
- List anything in the design you could NOT match and why.
```

That last line matters: it converts silent AI compromises into a visible list you triage instead of discover.

### Template 3 — Delivery notes (`delivery-notes.md`)

```markdown
# Delivery — [section name] · [date]
Preview: [theme preview link]

## What was built
[2–3 sentences, plain language]

## How to edit it
Theme editor → [where] → settings: [one line per non-obvious setting]

## Assumptions made
[carried over from the build spec — what needs their confirmation]

## Notes
[e.g., "Recommend image uploads ≤200 KB for this slot."]
Loom walkthrough: [placeholder — see T7.2]
```

## 4. Claude Code drill — rep #1, end to end

### Pick a real frame (~15 min)

Open **Figma Community** and duplicate any free file containing a section-sized design with: **a repeating unit** (cards / steps / logos), **at least one image**, and **a CTA**. Good searches: "landing page sections", "ecommerce homepage", "features section". Pick ONE frame — resist redesigning it; on client work the design is a given. *(No Figma access today? Use this written frame instead: a 3-step "How it works" strip — centered heading + subtext, three numbered cards each with icon, title, two lines of text, and a centered button below; 64px section padding, 32px card gap, cards stack on mobile.)*

### Run the method, timestamped

Work through **Stages 0–5 exactly as written above**, and write down the clock time when each stage starts. No skipping Stage 1 because you're eager to prompt — the spec-first discipline is the product you're installing.

- Stage 1 output → Template 1, committed as `notes/t2-1-build-spec.md`
- Stage 3 → Template 2 with your values; full review protocol; gap list written down, then burned down
- Stage 4 → all four widths + merchant test + Theme Check + console + Lighthouse glance
- Stage 5 → Template 3, committed as `notes/t2-1-delivery-notes.md`
- Everything on branch `t2-1-figma-rep-1`

### The retro (10 min — do not skip)

At the bottom of the delivery notes, add a **Retro** block: total time · time per stage · where the time actually went · what you'd systematize. Rep #1's retro is the baseline every later rep beats.

### The prescription

This method only becomes *fast* through repetition: **one frame per day for the next five working days**, full method every time, retro every time. By rep #5 the 2–4 hour target should be in reach — and those five sections become capstone material and portfolio evidence. (Vary them: one testimonial wall, one image-with-text hero, one logo bar, one pricing strip, one of your choice. At least one built for the Horizon playground using T1.6 conventions.)
